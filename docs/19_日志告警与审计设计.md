# 第19章 日志、告警与审计设计

## 19.1 概述

本章定义 MRSS 的应用日志、设备日志、通信日志、告警模型、阈值处理、告警生命周期、审计事件、Outbox、通知和查询设计。日志用于诊断，告警用于运行处置，审计用于追踪责任，三者不能相互替代。

一期告警覆盖系统资源、设备连接、设备故障、GAM1 测量、任务、通信、安全、急停、数据库和配置。告警数据统一写入 PostgreSQL，普通日志按文件或日志系统轮转。

## 19.2 设计目标

1. 日志结构统一、可检索、可脱敏。
2. 告警有稳定 alarm_key、来源、级别、当前态和事件历史。
3. 支持三档和五档告警策略。
4. 支持百分比、容量、测量值和离散状态阈值。
5. 支持磁盘、CPU、内存和传感器值统一表达。
6. 告警产生、升级、确认、恢复和关闭均可追溯。
7. 急停和安全告警优先于普通告警。
8. 告警去重、抖动抑制和重复提醒可配置。
9. 审计记录控制、认证、配置、模式、资源和安全操作。
10. 审计事实与业务事务关联，推送失败不改变事实。
11. 设备故障按实例隔离，避免告警风暴拖垮 Backend。
12. 提供查询、导出、统计和验收指标。

## 19.3 日志、告警、审计关系

~~~mermaid
flowchart LR
    EVENT[运行事件]
    LOG[结构化日志]
    ALARM[告警状态与事件]
    AUDIT[审计事实]
    NOTIFY[通知和WebSocket]
    HISTORY[历史查询]

    EVENT --> LOG
    EVENT --> ALARM
    EVENT --> AUDIT
    ALARM --> NOTIFY
    AUDIT --> HISTORY
    ALARM --> HISTORY
~~~

日志可以丢失低价值诊断信息；告警和审计的关键事实必须有持久化和补偿策略。

## 19.4 结构化日志

日志字段：

~~~text
timestamp
level
event_name
component
thread
trace_id
operation_id
task_id
device_id
error_code
duration_ms
message
attributes
~~~

事件名使用稳定的小写或大写枚举，不使用自由文本作为唯一检索依据。

级别：

| 级别 | 使用 |
| --- | --- |
| TRACE | 深度开发诊断 |
| DEBUG | 调试细节 |
| INFO | 生命周期、正常业务摘要 |
| WARN | 可恢复异常、降级 |
| ERROR | 业务失败、组件故障 |
| FATAL | 进程无法安全继续 |

## 19.5 日志脱敏

禁止写入：

- 明文密码；
- Access/Refresh Token；
- JWT 完整内容；
- 数据库连接串和密码；
- 设备 SDK 密钥；
- 未授权的图片绝对路径；
- 用户敏感信息；
- 原始硬件安全输入细节。

脱敏方法包括字段替换、哈希、截断和枚举化。日志脱敏发生在 Logger 边界，调用方不能依赖“自己记得脱敏”。

## 19.6 日志输出和轮转

一期支持：

~~~text
stderr/stdout
rotating file
structured json line
~~~

日志文件目录、大小、保留天数和压缩策略由部署配置。日志轮转失败产生 LOG_ROTATION_FAILED，但不能停止控制线程。磁盘剩余空间低于阈值时降低普通日志级别并触发告警。

### 19.7.3 AlarmEvent

事件类型：

~~~text
RAISED
ESCALATED
REPEATED
ACKNOWLEDGED
RECOVERED
CLEARED
SUPPRESSED
UNSUPPRESSED
~~~

首次发生时间不能被重复事件覆盖。

## 19.8 告警级别

统一内部级别：

~~~text
INFO
WARNING
ERROR
CRITICAL
FATAL
~~~

一期可以对外展示三档：

| 三档 | 内部映射 |
| --- | --- |
| WARNING | WARNING |
| ERROR | ERROR |
| FATAL | CRITICAL/FATAL |

五档模式使用 INFO、WARNING、ERROR、CRITICAL、FATAL。配置中声明启用的档位，业务 UI 不自行推断。

## 19.9 阈值节点

数值型阈值可以使用统一节点：

~~~text
0
10
100
1000
10000
100000
~~~

这组节点只是配置范围和示例，不代表所有传感器使用相同的单位或默认阈值。每个阈值必须绑定 module、name、type、unit 和方向。

支持方向：

~~~text
GREATER_THAN
GREATER_EQUAL
LESS_THAN
LESS_EQUAL
OUTSIDE_RANGE
INSIDE_RANGE
CHANGE_RATE
STALE
~~~

## 19.10 统一指标模型

~~~text
AlarmMetricData {
    robot_id
    module
    name
    type
    timestamp
    value
    unit
    extra_info
}
~~~

一期设备使用 device_id 作为主体，兼容已有 robot_id 字段时在映射层转换。系统资源示例：

~~~text
module=system, name=cpu_usage, type=percent, unit=%
module=system, name=memory_usage, type=percent, unit=%
module=system, name=disk_usage, type=percent, unit=%
module=system, name=disk_free, type=size, unit=MB
module=sensor, name=radiation, type=value, unit=uSv/h
~~~

单位不一致时不允许比较，配置加载时拒绝非法组合。

## 19.11 百分比和容量告警

百分比配置：

~~~text
enable
warning_percent
error_percent
fatal_percent
remind_interval_ms
~~~

容量配置：

~~~text
enable
warning_mb
error_mb
fatal_mb
remind_interval_ms
direction: ABOVE or BELOW
~~~

磁盘使用率和磁盘可用空间不能同时用相同方向解释。配置必须显式声明 metric 和 direction，避免把“可用空间低于阈值”误当成“使用率超过阈值”。

## 19.12 传感器告警

GAM1 等传感器告警输入至少包含 value、unit、quality 和 measured_at。处理规则：

1. quality=BAD 时产生 SENSOR_DATA_BAD；
2. quality=STALE 时产生 SENSOR_DATA_STALE；
3. quality=GOOD 且超过阈值时产生测量告警；
4. 单位不匹配时产生 CONFIG_INVALID，不执行比较；
5. 值为 NaN/Infinity 时拒绝；
6. 恢复必须连续满足恢复条件或配置的恢复窗口；
7. 变化率阈值需要至少两个有效样本。

## 19.13 告警状态机

~~~mermaid
stateDiagram-v2
    [*] --> INACTIVE
    INACTIVE --> ACTIVE: threshold reached
    ACTIVE --> ACTIVE: repeated sample
    ACTIVE --> ESCALATED: higher level
    ACTIVE --> ACKED: operator acknowledge
    ACKED --> ACKED: still active
    ACTIVE --> RECOVERED: recovery condition
    ACKED --> RECOVERED: recovery condition
    RECOVERED --> INACTIVE: close policy
    ACTIVE --> SUPPRESSED: suppression policy
    SUPPRESSED --> ACTIVE: suppression released and condition active
~~~

确认不清除告警；恢复不等于人工确认。

## 19.14 去重和抖动抑制

唯一键：

~~~text
alarm_key + device_id + source
~~~

去重策略：

- 相同状态和级别只更新 last_seen；
- 级别提升立即生成 ESCALATED；
- 条件短时抖动使用 debounce；
- 恢复后再次触发生成新的 active_since；
- remind_interval 到期生成 REPEATED；
- 同一设备告警超过批量上限时按优先级合并通知，但数据库事件仍保留关键变化。

## 19.15 告警确认

确认接口：

~~~text
POST /api/alarms/{alarm_id}/ack
~~~

确认需要 alarm:ack 权限和资源范围。确认记录 actor_id、reason、time、trace_id。重复确认返回当前状态，不重复创建事实。

以下告警通常不允许普通用户清除：

- 硬件急停；
- 安全输入无效；
- 设备停止未知；
- 安全配置错误；
- 数据库 schema 不一致。

这些告警只能在根因恢复并通过安全/维护流程后自动或授权清除。

## 19.16 通知策略

通知分层：

| 级别 | WebSocket | 页面提示 | 外部通知 |
| --- | --- | --- | --- |
| INFO | 可选 | 可选 | 否 |
| WARNING | 是 | 是 | 配置决定 |
| ERROR | 是 | 是 | 配置决定 |
| CRITICAL | 是 | 强提示 | 是 |
| FATAL | 是 | 强提示并锁定操作 | 是 |

通知发送失败不改变 AlarmState。Outbox 保存通知任务并按幂等键重试。

## 19.17 审计模型

审计事件适用于：

- 登录、退出、权限拒绝；
- 用户、角色和配置变更；
- 模式切换；
- OWNER/资源获取和释放；
- MOVEJ、JOG、STOP、拍照、采样；
- 任务创建、启动、取消和恢复；
- 急停、Permit 变化和安全复位；
- 告警确认、清除和抑制；
- 数据导出、备份和恢复；
- 进程启动和关闭。

审计字段：

~~~text
audit_id
occurred_at
actor_type
actor_id
session_id
action
resource_type
resource_id
operation_id
trace_id
result
reason
before_digest
after_digest
metadata
~~~

## 19.18 审计一致性

控制操作的推荐事务：

1. 生成 operation；
2. 写入控制请求事实；
3. 写入审计事实；
4. 写入 Outbox 事件；
5. 提交；
6. 调用设备；
7. 写入最终结果和后续审计。

无法在设备调用前完成数据库提交时，至少先生成本地 operation_id 和安全日志，完成后补写。结果 UNKNOWN 不能伪装成成功审计。

## 19.19 Outbox

Outbox 用于可靠发布告警、审计摘要、WebSocket 补发和外部通知。

~~~text
OutboxEvent {
    event_id
    event_type
    aggregate_type
    aggregate_id
    payload
    status
    attempts
    next_attempt_at
    last_error
    created_at
}
~~~

发送器：

1. 按优先级取事件；
2. 使用 event_id 幂等发送；
3. 成功标记 SENT；
4. 失败按退避重试；
5. 超过上限标记 FAILED 并产生 OUTBOX_FAILED；
6. 安全事件失败时保留本地补偿和人工处置入口。

## 19.20 日志与告警关联

日志、告警和审计通过 trace_id、operation_id、device_id、task_run_id 关联。前端显示告警时可以查看：

- 首次发生和最近时间；
- 当前值和单位；
- 来源设备；
- 关联任务和操作；
- 相关安全事件；
- 最近错误日志摘要；
- 确认和恢复记录。

日志查询不能让普通用户看到超出权限范围的设备凭据。

## 19.21 告警风暴控制

控制措施：

- 每个 alarm_key 独立去重；
- 通知按级别限流；
- 相同设备同类告警可聚合；
- 安全告警不可被普通聚合隐藏；
- 告警队列有容量和优先级；
- 数据库故障时只保留高价值安全事实；
- 风暴开始、抑制、恢复都产生系统告警；
- 解除抑制后补发摘要。

## 19.22 查询和统计接口

~~~text
GET /api/alarms
GET /api/alarms/{alarm_id}
GET /api/alarms/history
GET /api/alarms/statistics
POST /api/alarms/{alarm_id}/ack
POST /api/alarms/{alarm_id}/clear
GET /api/audit/events
GET /api/audit/statistics
GET /api/logs/query
~~~

查询条件支持时间、设备、模块、级别、状态、alarm_key、actor、operation_id 和 trace_id。日志导出需要单独权限并记录审计。

## 19.23 保留与归档

- 安全、急停、权限变更和审计长期保留；
- 告警事件按合规和项目周期保留；
- 高频重复通知可以压缩，但首次、升级、恢复和确认不可丢；
- 普通日志按天轮转；
- 归档前生成 checksum 和元数据；
- 删除操作必须记录删除范围、操作者和策略版本。

## 19.24 故障处理

| 故障 | 处理 |
| --- | --- |
| Logger 磁盘满 | 降低普通日志，保留安全错误并告警 |
| 告警数据库断开 | 内存/本地有界缓冲，安全事件优先 |
| Outbox 发送失败 | 退避、重试、FAILED 告警 |
| 通知服务断开 | 不改变告警事实 |
| 设备事件乱序 | 按版本/时间拒绝回退 |
| 告警配置错误 | 启动拒绝或禁用该规则并告警 |
| 告警风暴 | 聚合通知，保留关键事件 |
| 审计写入失败 | 标记审计降级，不伪造成功 |
| 系统关闭 | 先刷写关键安全和审计事件 |

## 19.26 验收追踪

- 日志、告警、审计职责明确；
- 五类一期设备和系统资源可产生统一告警；
- 三档和五档可配置；
- 阈值带单位和方向；
- 触发、升级、确认、恢复和清除可追溯；
- 急停和安全告警不被抑制隐藏；
- 审计包含控制、模式、资源、认证和配置变更；
- Outbox 支持可靠补发；
- 告警风暴不会阻塞控制和安全路径。

## 19.27 本章小结

本章完成了 MRSS 日志、告警与审计设计，定义了结构化日志、脱敏、告警定义/状态/事件、三档五档级别、阈值节点、百分比/容量/传感器指标、去重抑制、确认恢复、通知、审计和 Outbox。系统通过 trace_id、operation_id 和设备/任务标识把运行现象、处置告警和责任审计关联起来。
