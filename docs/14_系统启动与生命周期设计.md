# 第14章 系统启动与生命周期设计

## 14.1 概述

本章定义 MRSS Backend 从进程启动、配置加载、依赖初始化、组件启动、就绪服务、运行监控、故障降级到关闭退出的完整生命周期。生命周期设计的目标是让启动失败可诊断、运行状态可观测、停止过程可控，并保证 STOP、三源急停和设备安全释放优先于普通业务清理。

一期不启动 IOC。Backend 直接通过 Device 和 Access 连接仿真或真实设备；同一进程可配置全仿真、全真实或混合设备。

## 14.2 生命周期目标

1. 任何启动失败都有明确阶段和错误码。
2. 配置、数据库、通信和设备初始化顺序固定。
3. readiness 只有在系统满足接收业务的条件后才为 true。
4. 单设备失败不会自动导致整个系统退出，除非违反全局安全前提。
5. 数据库失败不阻塞安全停止。
6. 进程收到 SIGTERM 后执行有序关闭。
7. 重启后能够恢复任务、租约、告警和设备状态。
8. systemd、容器和手工启动行为一致。
9. 启动日志不输出密钥、密码和设备凭据。
10. 模式、急停和 Permit 初始状态遵循 fail-safe 规则。

## 14.4 进程阶段

~~~text
PROCESS_CREATED
CONFIG_LOADING
CONFIG_VALIDATING
CORE_INITIALIZING
DATABASE_INITIALIZING
COMMUNICATION_INITIALIZING
ACCESS_INITIALIZING
DEVICE_INITIALIZING
CONTROLLER_INITIALIZING
SERVICE_INITIALIZING
API_INITIALIZING
STARTING
DEGRADED
READY
STOP_REQUESTED
STOPPING
STOPPED
FAILED
~~~

DEGRADED 是可运行但部分设备或非关键依赖异常的状态。FAILED 是进程不能安全提供基本服务的状态。

## 14.5 启动总流程

1. 解析命令行参数；
2. 建立最小 stderr 日志；
3. 加载配置文件和环境覆盖；
4. 校验配置版本、路径、端口和秘密引用；
5. 初始化结构化日志、时钟、指标和追踪；
6. 注册信号处理器；
7. 初始化 db 和 schema 检查；
8. 初始化 Communication；
9. 创建 Access 工厂；
10. 创建 Device 实例；
11. 初始化 Controller、Scheduler 和 SafetyService；
12. 初始化 auth、service 和 api；
13. 恢复设备快照、任务和告警；
14. 启动后台线程；
15. 执行健康检查；
16. 设置 readiness；
17. 进入主循环。

## 14.6 配置检查

启动时必须检查：

| 配置 | 检查 |
| --- | --- |
| server | HTTP、WS、TCP、UDP 地址和端口 |
| database | PostgreSQL 地址、端口、库名、凭据引用 |
| auth | JWT key_id、Token TTL、密码策略 |
| devices | 设备 ID、类型、mode、访问配置 |
| safety | 初始模式、Permit、急停策略 |
| paths | 日志、图片、临时、备份目录 |
| scheduler | 线程、队列、周期和并发上限 |
| limits | 请求、队列、历史查询和文件大小 |
| version | 配置 schema 版本和兼容范围 |

未知字段根据配置策略处理。安全相关配置缺失时必须拒绝启动，不使用“宽松默认值”。

## 14.7 数据库启动

db 初始化顺序：

1. 创建连接池；
2. 测试最小查询；
3. 获取 schema 版本；
4. 执行已批准的迁移；
5. 校验关键表、索引和约束；
6. 初始化 Repository；
7. 启动持久化队列；
8. 记录数据库能力快照。

如果 PostgreSQL 连接失败，系统可以在维护模式启动用于诊断，但不能将 readiness 标记为可执行控制。是否允许只读启动由部署配置决定。

## 14.8 Communication 启动

Communication 先绑定监听端口，再启动连接管理线程。启动失败分类：

- 端口被占用；
- 地址非法；
- 权限不足；
- TLS 配置错误；
- 线程创建失败；
- WebSocket 路由注册失败。

HTTP 健康端口可以与业务端口分离。安全停止接口必须在主业务队列异常时仍可被处理，必要时使用独立控制通道。

## 14.9 Access 和 Device 启动

AccessFactory 根据设备配置创建：

~~~text
R1         -> RealmanAdapter or SimArmAdapter
R2         -> RealmanAdapter or SimArmAdapter
HIK_FIX1   -> HikvisionFixedAdapter or SimCameraAdapter
HIK_PTZ1   -> HikvisionPtzAdapter or SimPtzAdapter
GAM1       -> RadiationAdapter or SimRadiationAdapter
~~~

启动时不直接把所有设备标记为 ONLINE。正确顺序是：

1. CREATED；
2. CONFIGURED；
3. CONNECTING；
4. CONNECTED 或 OFFLINE；
5. INITIALIZED；
6. READY/FAULT。

仿真设备也执行同一状态检查，只是连接和动作由仿真时钟与状态机提供。

## 14.10 初始安全状态

进程启动时：

- 全局系统模式默认为 SAFE_INIT 或 MAINTENANCE；
- 软件急停状态根据持久化和硬件输入确定；
- 硬件急停输入不可读取时按触发处理；
- Safety Permit 初始为 0，完成全部检查后才能变为 1；
- 设备未确认状态前禁止运动；
- 自动任务不在启动瞬间自动执行；
- 所有恢复动作必须有事件和审计。

启动不是安全复位。安全复位需要独立的授权和第17章定义的条件。

## 14.11 Controller 启动

Controller 创建每个设备的命令队列和停止通道。启动时：

1. 建立设备上下文；
2. 清理上次未完成的临时命令；
3. 将未知运行中的操作标记为 UNKNOWN；
4. 对设备读取状态；
5. 根据设备状态决定是否需要 STOP；
6. 注册状态回调；
7. 启动每设备执行线程或执行器；
8. 发布 DEVICE_READY 或 DEVICE_DEGRADED。

上次进程异常退出后，不能假设机械臂已经停在安全位置；必须读取真实状态或仿真状态，再决定恢复策略。

## 14.12 任务恢复

启动恢复分为三类：

| 数据 | 恢复策略 |
| --- | --- |
| 未完成 TaskRun | 标记 RECOVERY_PENDING，默认不自动继续 |
| 未确认 Operation | 标记 UNKNOWN，进入查询队列 |
| 未释放 Resource Lease | 按租约过期或启动清理策略释放 |
| 活跃 Alarm | 读取当前设备状态后重算 |
| 定时任务 | 依据 missed policy 决定跳过、补跑或等待 |
| Outbox 事件 | 继续发送，保证幂等 |

一期默认不在 Backend 重启后自动恢复运动中的任务，必须由运维人员或策略明确确认后重新启动。

## 14.13 Ready 条件

readiness=true 的最低条件：

1. 配置验证通过；
2. db 达到部署要求；
3. api 和 WebSocket 监听成功；
4. core 执行器正常；
5. auth 可执行验证；
6. SafetyService 已进入受控初始状态；
7. 必要设备注册完成；
8. Controller 和 Scheduler 已启动；
9. 没有阻止所有业务的全局故障。

某个可选设备离线时可以 READY_DEGRADED，但接口必须在响应中声明设备不可用。

## 14.14 Health 与 Readiness

Health 反映进程是否存活：

~~~text
GET /api/system/health
~~~

Readiness 反映能否接收某类业务：

~~~text
GET /api/system/readiness
~~~

响应区分：

~~~json
{
  "process": "UP",
  "readiness": "DEGRADED",
  "database": "UP",
  "communication": "UP",
  "safety": "SAFE_INIT",
  "devices": {
    "R1": "READY",
    "R2": "OFFLINE",
    "HIK_FIX1": "READY",
    "HIK_PTZ1": "READY",
    "GAM1": "READY"
  },
  "accept_control": false
}
~~~

## 14.15 运行期状态转换

~~~mermaid
stateDiagram-v2
    [*] --> STARTING
    STARTING --> READY: required checks pass
    STARTING --> DEGRADED: optional dependency unavailable
    STARTING --> FAILED: mandatory check fails
    READY --> DEGRADED: device or dependency fault
    DEGRADED --> READY: recovery succeeds
    READY --> STOP_REQUESTED: signal or admin shutdown
    DEGRADED --> STOP_REQUESTED: signal or admin shutdown
    STOP_REQUESTED --> STOPPING
    STOPPING --> STOPPED
    STOPPING --> FAILED: timeout with recorded risk
    FAILED --> STOPPING: supervisor cleanup
    STOPPED --> [*]
~~~

## 14.16 故障隔离

设备级故障处理：

1. 更新设备状态为 FAULT 或 OFFLINE；
2. 撤销该设备的普通执行许可；
3. 取消或失败该设备相关 operation；
4. 释放该设备资源；
5. 产生告警和审计；
6. 保持其他设备运行；
7. 判断协同任务是否需要整体失败；
8. 继续提供查询和安全停止。

系统级故障只有在安全控制、线程运行时或配置一致性无法保证时才进入 FAILED。

## 14.17 信号处理

信号处理线程只做：

- 记录信号；
- 设置 shutdown flag；
- 通知主循环；
- 唤醒等待条件变量。

不得在 POSIX signal handler 中调用数据库、malloc、日志库复杂函数或设备 SDK。主线程收到 flag 后执行正常 shutdown。

## 14.18 关闭流程

~~~mermaid
sequenceDiagram
    participant OS as systemd
    participant B as Backend
    participant S as Scheduler
    participant C as Controller
    participant D as Device
    participant A as Audit
    participant DB as db

    OS->>B: SIGTERM
    B->>B: readiness=false
    B->>S: stop accepting new tasks
    B->>C: request safe stop
    C->>D: STOP
    D-->>C: stopped or timeout
    B->>A: flush critical events
    B->>DB: commit shutdown snapshot
    B->>B: close communication and executors
    B-->>OS: exit
~~~

关闭超时后继续退出，但必须记录未确认设备、未刷新的审计和数据库状态。systemd 的 TimeoutStopSec 应大于正常安全停止预算。

## 14.19 systemd 部署约束

服务单元建议包括：

~~~ini
[Service]
Type=simple
ExecStart=/opt/mrss/bin/mrss_backend --config /etc/mrss/config.yaml
Restart=on-failure
RestartSec=3
LimitNOFILE=65536
NoNewPrivileges=true
PrivateTmp=true
~~~

用户、目录、端口、日志和数据库权限由部署章节统一定义。Restart=on-failure 不能替代应用自身的恢复和故障隔离。

## 14.20 命令行

~~~text
mrss_backend --config PATH
mrss_backend --check-config --config PATH
mrss_backend --print-version
mrss_backend --migrate --config PATH
mrss_backend --maintenance --config PATH
~~~

--check-config 只加载和验证配置，不绑定业务端口、不执行设备动作。--migrate 只在明确运维操作下执行数据库迁移。

## 14.21 生命周期审计

至少记录：

- 启动开始、配置通过和启动完成；
- 组件初始化失败；
- readiness 变化；
- 设备上线、离线和恢复；
- 进入维护和安全初始状态；
- 收到关闭信号；
- 安全停止结果；
- 进程退出和未确认风险。

## 14.22 测试设计

1. 正常启动和关闭；
2. 配置缺失、版本不兼容和秘密引用错误；
3. 数据库未启动、迁移失败和连接池耗尽；
4. 端口占用和 TLS 错误；
5. 单设备离线、设备恢复和设备故障；
6. 上次运行存在未完成任务；
7. 信号重复、关闭超时和强制终止；
8. ready/degraded/failed 状态；
9. systemd 重启和日志轮转；
10. 仿真/真实/混合设备启动矩阵；
11. 启动后 Permit=0、急停锁存和安全复位；
12. STOP 不被数据库或普通队列阻塞。

## 14.23 验收追踪

- 进程启动阶段和错误码可追踪；
- 设备初始化不伪造 ONLINE；
- readiness 反映真实可用能力；
- 单设备故障不拖垮其他设备；
- 重启后未完成任务不会自动危险续跑；
- SIGTERM 会执行安全停止和关键审计刷写；
- 无 IOC 依赖仍可完成一期闭环；
- systemd 和手工启动配置一致。

## 14.24 本章小结

本章定义了 MRSS Backend 的启动、初始化、就绪、降级、故障隔离、恢复和关闭全过程，明确了配置、db、Communication、Access、Device、Controller、service、api 的依赖顺序和生命周期语义。系统启动时默认处于受控安全状态，安全许可必须经过检查，设备故障按实例隔离，停止流程优先保证设备安全和关键审计。
