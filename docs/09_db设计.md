# 第9章 db 设计

## 9.1 概述

`db` 模块是 MRSS Backend 的统一数据访问层，负责 PostgreSQL 连接管理、事务控制、SQL 执行、数据模型映射、Repository 实现、数据库迁移、历史数据查询和持久化故障处理。

本章的 `db` 不是数据库服务器本身，也不承担用户认证、任务调度或设备控制业务。它向上为 service、Controller 和审计/告警组件提供稳定的 Repository 接口，向下通过 SOCI 访问 PostgreSQL。上层模块不得直接依赖 `soci::session`、`libpq`、数据库连接字符串或具体 SQL。

一期数据库采用 PostgreSQL。C++ 数据访问采用 SOCI 的 PostgreSQL 专用后端 `SOCI_POSTGRESQL`，不通过 ODBC 中间层。SOCI 负责数据库访问抽象，PostgreSQL 负责事务数据库、并发控制、索引、备份和持久化存储。

一期不引入 IOC。设备状态、任务状态、采样记录、告警记录和审计记录由 Backend 统一落库；后续接入真实设备或 EPICS Access 时，数据库接口、表结构和业务流程保持不变。

## 9.2 设计目标

`db` 模块需要满足以下目标：

1. 对上层屏蔽 PostgreSQL、SOCI 和具体 SQL 实现。
2. 提供统一的连接池、事务、超时、重试和异常转换机制。
3. 使用 Repository 模式隔离业务模型与数据库表结构。
4. 支持用户、角色、设备、任务、任务执行、动作、采样、资源、告警、审计和系统配置等核心数据持久化。
5. 保证任务创建、任务点位和动作配置的一致性。
6. 保证告警、任务事件和审计事件可以通过 `trace_id`、`task_id`、`operation_id` 关联。
7. 在数据库暂时不可用时，不阻塞设备安全停止和 Backend 主循环。
8. 支持分页查询、时间范围查询、条件过滤和稳定排序。
9. 支持历史数据保留、归档、备份和恢复。
10. 支持仿真、真实和混合设备使用同一套数据库模型。
11. 为数据库迁移、回滚和版本检查提供明确流程。
12. 为单元测试、集成测试和故障注入提供可替换的数据访问端口。

## 9.3 设计原则

### 9.3.1 业务模型与存储模型分离

`Task`、`DeviceSnapshot`、`AlarmRecord` 等 C++ 对象是业务模型，`task`、`device_state_history`、`alarm_record` 等是存储模型。Repository 负责两者之间的映射，service 不拼接列名、不处理数据库字段类型转换。

### 9.3.2 事务边界显式

跨多个 Repository 的原子操作必须由 service 或 `UnitOfWork` 显式创建事务。单个 Repository 不得偷偷开启独立事务后再参与外层业务操作，否则会导致任务和任务点位出现部分提交。

### 9.3.3 读写分离语义

一期可以使用同一个 PostgreSQL 实例，但代码中区分读端口和写端口。查询接口不得隐式修改数据；写接口必须明确记录事务、操作者和结果。

### 9.3.4 安全参数绑定

所有外部输入使用 SOCI 绑定变量或白名单构造的 SQL 片段。禁止把用户输入、设备 ID、排序字段和过滤值直接拼入 SQL。

### 9.3.5 时间与时区统一

对外事件时间使用 UTC 语义。数据库中的业务时间统一使用 `TIMESTAMPTZ`；与现有系统兼容的毫秒时间戳字段可以保留为 `BIGINT`，但必须明确其单位为 Unix milliseconds。

### 9.3.6 可追踪

写操作至少携带 `trace_id`。控制命令、任务运行、设备事件、告警和审计事件通过 `trace_id`、`operation_id` 或业务主键形成关联链。

### 9.3.7 单设备故障隔离

R1、R2、HIK_FIX1、HIK_PTZ1 和 GAM1 的状态及历史记录按设备隔离。单个设备的写入异常不能回滚其他设备已经完成的独立记录，也不能阻塞 STOP、急停和 Backend 关闭。

### 9.3.8 结果不确定时不伪造成功

数据库提交结果未知时，调用方不能直接把任务或动作标记为成功。应通过事务状态、幂等键或补偿查询确认最终结果。

## 9.4 模块职责边界

### 9.4.1 db 负责的内容

| 类别 | 职责 |
| --- | --- |
| 连接 | 创建、检查、复用和关闭 PostgreSQL 连接 |
| 连接池 | 限制并发连接数，借出、归还和失效连接 |
| 事务 | begin、commit、rollback、超时和嵌套语义 |
| 执行 | 参数绑定、批量执行、查询、命令超时 |
| 映射 | 数据库行与 C++ 值对象互转 |
| Repository | 对用户、设备、任务、告警、审计等提供持久化接口 |
| 迁移 | 初始化、版本升级、结构校验和回滚保护 |
| 历史 | 条件查询、分页、时间范围和归档 |
| 故障处理 | 断线检测、有限重试、降级、补写和诊断 |
| 可观测性 | 连接、事务、查询耗时、失败和队列指标 |

### 9.4.2 db 不负责的内容

1. 不验证 JWT，不解析用户角色，不实现 RBAC 决策。
2. 不判断设备命令是否允许执行，不实现 OWNER 仲裁。
3. 不编排双臂协同，不管理任务状态机。
4. 不连接机械臂、相机、辐射传感器或 EPICS PV。
5. 不直接保存图片、视频和大体积原始文件，只保存 Resource 元数据和受控引用。
6. 不把数据库连接异常转换为设备急停成功。
7. 不将 PostgreSQL 存储目录配置交给 SOCI；数据目录由 PostgreSQL、systemd、容器或部署脚本管理。
8. 不在查询接口中夹带隐式写操作。

## 9.8 数据库部署边界

### 9.8.1 一期部署拓扑

~~~mermaid
flowchart LR
    BACKEND["Backend"]
    POOL["ConnectionPool"]
    PG["PostgreSQL 16"]
    DISK["PostgreSQL data directory"]
    BACKUP["Backup files"]

    BACKEND --> POOL
    POOL --> PG
    PG --> DISK
    PG --> BACKUP
~~~

推荐启动顺序：

1. 挂载数据库数据盘或准备 PostgreSQL 存储目录。
2. 启动 PostgreSQL 16 集群。
3. 执行连接、版本和权限健康检查。
4. 执行只允许前进的数据库迁移。
5. 启动 Backend 的 db 模块。
6. 初始化设备注册表、状态缓存和其他 Backend 模块。
7. 启动 Communication 和对外接口。

### 9.8.2 存储位置责任

PostgreSQL 的整体数据目录由 PostgreSQL 配置、systemd、Docker volume 或部署脚本管理。SOCI 只能执行数据库级 SQL，不能把整个 PostgreSQL 数据目录移动到指定磁盘。

需要单独放置部分大表或索引时，可以由运维脚本创建 PostgreSQL TABLESPACE，再通过迁移 SQL 将指定表或索引放置到该表空间。该策略不改变 db 的 Repository 接口。

### 9.8.3 一期数据库原则

| 项目 | 一期决定 |
| --- | --- |
| 目标数据库 | PostgreSQL 16 |
| C++ 访问库 | SOCI |
| SOCI 后端 | SOCI_POSTGRESQL |
| ODBC | 不作为一期中间层 |
| SQLite | 仅可用于本地单元测试或开发辅助，不作为正式部署数据库 |
| IOC | 不引入 |
| 图片/视频 | 文件或对象存储；数据库保存引用和元数据 |
| 主键 | PostgreSQL 序列或 UUID，按表的访问特点选择 |
| 时间 | TIMESTAMPTZ，兼容字段保留毫秒时间戳语义 |

## 9.10 DBManager 类设计

### 9.10.1 类职责

DBManager 是 db 模块的生命周期入口，负责配置校验、连接池创建、迁移执行、健康检查、Repository 工厂注册和关闭协调。

DBManager 不暴露 soci::session，不接收业务 SQL，不执行用户、任务或设备的领域判断。

### 9.10.2 类定义

~~~cpp
class DBManager {
~~~

### 9.10.4 初始化流程

~~~text
读取 DBConfig
  -> 校验驱动、端口、连接池边界和超时
  -> 创建 ConnectionPool
  -> 建立管理连接
  -> 检查 PostgreSQL 版本和扩展
  -> 执行 migration
  -> 创建 Repository 实例
  -> 执行健康查询
  -> 发布 db.ready
~~~

迁移失败时，DBManager 进入 FAILED，Backend 不得以不完整的表结构启动。数据库暂时断线时，允许进入 DEGRADED，但必须禁止依赖持久化成功才能确认的业务操作。

## 9.11 ConnectionPool 类设计

### 9.11.1 类职责

ConnectionPool 负责限制 PostgreSQL 连接数量和生命周期，向事务和 Repository 提供短生命周期连接。连接池不保存业务状态，不缓存用户、任务和设备对象。

### 9.11.2 类定义

~~~cpp
class ConnectionPool {
public:
    ConnectionPool(DBConfig config, std::shared_ptr<ILogger> logger);
    ~ConnectionPool();

    void start();
    void stop(std::chrono::milliseconds deadline);

    ConnectionGuard acquire(std::chrono::milliseconds timeout);
    void invalidate(ConnectionId id);
    PoolStats stats() const;

private:
    std::unique_ptr<DBConnection> createConnection();
    bool validate(DBConnection& connection);
    void reapIdleConnections();

    DBConfig config_;
    std::vector<std::unique_ptr<DBConnection>> idle_;
    std::unordered_map<ConnectionId, ConnectionLease> active_;
    std::condition_variable available_;
    mutable std::mutex mutex_;
    bool stopping_{false};
};
~~~

### 9.11.3 连接借用流程

~~~mermaid
sequenceDiagram
    participant Repo as Repository
    participant Pool as ConnectionPool
    participant Conn as DBConnection
    participant PG as PostgreSQL

    Repo->>Pool: acquire(timeout)
    Pool->>Pool: select idle connection
    Pool->>Conn: validate()
    Conn->>PG: SELECT 1
    PG-->>Conn: OK
    Conn-->>Pool: valid
    Pool-->>Repo: ConnectionGuard
    Repo->>Conn: execute/query
    Repo-->>Pool: guard released
    Pool->>Pool: reset session state
~~~

每次连接归还前必须清理事务状态、临时会话参数和未消费的结果集。发生 SQL 异常、连接断开或协议错误时，连接不能直接回到空闲队列，必须标记为失效并重建。

### 9.11.4 连接池约束

1. pool_min_size <= pool_max_size。
2. pool_max_size 必须根据 Backend 线程数和 PostgreSQL max_connections 计算。
3. 单个请求不能永久占用连接。
4. 连接获取超时必须返回明确错误 DB_POOL_EXHAUSTED。
5. 连接断开不能通过复用原对象伪造恢复，必须创建新连接。
6. 关闭阶段拒绝新的借用，并等待活动连接在截止时间内归还。

## 9.12 DBConnection 与 ConnectionGuard

~~~cpp
class DBConnection {
public:
    ConnectionId id() const;
    bool isHealthy() const;
    void setStatementTimeout(std::chrono::milliseconds timeout);
    void resetSession();

    soci::session& session();

private:
    ConnectionId id_;
    soci::session session_;
    std::chrono::steady_clock::time_point created_at_;
    std::chrono::steady_clock::time_point last_used_at_;
    std::atomic<bool> healthy_{true};
};

class ConnectionGuard {
public:
    ConnectionGuard(ConnectionPool& pool, DBConnection* connection);
    ~ConnectionGuard();

    DBConnection& operator*();
    DBConnection* operator->();
    void invalidate();

private:
    ConnectionPool* pool_;
    DBConnection* connection_;
    bool invalid_{false};
};
~~~

soci::session 只在 db 内部使用。任何跨线程传递 ConnectionGuard 的行为都视为错误；Repository 在当前调用上下文内完成 SQL 操作，长耗时设备控制不得持有数据库连接。

## 9.13 DBTransaction 类设计

### 9.13.1 类职责

DBTransaction 使用 RAII 管理事务。构造时开始事务，显式 commit() 才成功提交，析构时未提交则回滚。

~~~cpp
class DBTransaction {
public:
    explicit DBTransaction(ConnectionGuard connection);
    ~DBTransaction();

    DBTransaction(const DBTransaction&) = delete;
    DBTransaction& operator=(const DBTransaction&) = delete;

    void commit();
    void rollback() noexcept;
    void setTimeout(std::chrono::milliseconds timeout);
    void createSavepoint(std::string_view name);
    void rollbackToSavepoint(std::string_view name);
    bool committed() const;

private:
    ConnectionGuard connection_;
    bool committed_{false};
    bool rolled_back_{false};
};
~~~

### 9.13.2 事务规则

| 场景 | 事务要求 |
| --- | --- |
| 创建任务及其点位 | 一个事务 |
| 更新任务状态和写任务事件 | 一个事务 |
| 写告警及告警事件 | 一个事务 |
| 写单次传感器采样 | 可批量事务 |
| 写设备状态快照 | 可按设备或批次事务 |
| 写审计事件 | 尽量独立事务，不能回滚控制结果记录 |
| 设备控制命令 | 数据库事务不包围设备网络调用 |

数据库事务不能跨越机械臂运动、相机抓图或传感器等待。正确流程是：先提交命令受理记录，再调用设备；收到结果后开启新事务写入结果。

### 9.13.3 事务状态机

~~~mermaid

    ACTIVE --> COMMITTED: commit

    ACTIVE --> ROLLED_BACK: destructor
    ACTIVE --> FAILED: SQL error
~~~

## 9.14 UnitOfWork 设计

当一个业务操作需要调用多个 Repository 时使用 UnitOfWork：

~~~cpp
class UnitOfWork {
public:
    explicit UnitOfWork(ConnectionPool& pool);

    UserRepository& users();
    DeviceRepository& devices();
    TaskRepository& tasks();
    TaskRunRepository& taskRuns();
    AlarmRepository& alarms();
    AuditRepository& audits();

    void commit();
    void rollback() noexcept;

private:
    ConnectionGuard connection_;
    DBTransaction transaction_;
    UserRepository users_;
    DeviceRepository devices_;
    TaskRepository tasks_;
    TaskRunRepository task_runs_;
    AlarmRepository alarms_;
    AuditRepository audits_;
};
~~~

UnitOfWork 只在短事务内存在。禁止把它放进设备异步任务对象、WebSocket Session 或全局缓存中。

## 9.15 Repository 接口设计

### 9.15.1 通用返回模型

~~~cpp
template<typename T>
struct PageResult {
    std::vector<T> items;
    uint64_t total{0};
    uint32_t page{1};
    uint32_t page_size{50};
    bool has_more{false};
};

struct QueryRange {
    timestamp_t from{0};
    timestamp_t to{0};
    uint32_t page{1};
    uint32_t page_size{50};
    std::string order_by;
    bool descending{true};
};

struct RepositoryError {
    std::string code;
    std::string message;
    bool retryable{false};
    bool transaction_unknown{false};
};
~~~

### 9.15.2 Repository 约束

1. Repository 方法使用业务值对象和明确的过滤结构。
2. 不向 service 返回 soci::row。
3. 不接受任意 SQL 字符串作为普通业务参数。
4. 所有更新方法返回影响行数或明确的不存在结果。
5. 删除优先采用逻辑删除或归档，不直接删除审计、告警和任务运行历史。
6. 需要幂等的写入必须显式传入 idempotency_key。
7. 查询分页必须有稳定的唯一键作为第二排序条件。

## 9.16 SOCI 使用规范

### 9.16.1 参数绑定

~~~cpp
std::string device_id = record.device_id;
int state = static_cast<int>(record.state);
long long timestamp_ms = record.timestamp_ms;

sql << R"(
    INSERT INTO device_state_history(device_id, state, timestamp_ms)
    VALUES (:device_id, :state, :timestamp_ms)
)",
    soci::use(device_id, "device_id"),
    soci::use(state, "state"),
    soci::use(timestamp_ms, "timestamp_ms");
~~~

不得通过字符串拼接传入设备 ID、用户输入、错误消息或查询条件。

### 9.16.2 查询映射

~~~cpp
struct DeviceRow {
    std::string device_id;
    std::string device_type;
    int state{0};
    std::string backend;
    bool enabled{true};
    long long updated_at_ms{0};
};

DeviceRow row;
sql << R"(
    SELECT device_id, device_type, state, backend, enabled,
           (extract(epoch from updated_at) * 1000)::bigint
      FROM device
     WHERE device_id = :device_id
)",
    soci::into(row.device_id),
    soci::into(row.device_type),
    soci::into(row.state),
    soci::into(row.backend),
    soci::into(row.enabled),
    soci::into(row.updated_at_ms),
    soci::use(device_id, "device_id");
~~~

实际工程中应通过 RowMapper 统一处理 NULL、时间、JSONB、枚举、数组和字段缺失，不在每个 Repository 中重复实现转换。

### 9.16.3 批量写入

传感器采样、设备状态历史和任务事件通常使用批量绑定并包在一个短事务内：

~~~cpp
std::vector<std::string> device_ids;
std::vector<double> values;
std::vector<long long> timestamps;

sql << R"(
    INSERT INTO sensor_record(device_id, value, timestamp_ms)
    VALUES (:device_id, :value, :timestamp_ms)
)",
    soci::use(device_ids, "device_id"),
    soci::use(values, "value"),
    soci::use(timestamps, "timestamp_ms");
~~~

批量大小必须有上限，例如按 100～1000 条一批配置，避免单次事务持锁过久或 SQL 参数过大。

## 9.18 数据库命名规范

### 9.18.1 表和字段命名

1. 表名使用小写蛇形命名，例如 task_run、alarm_record。
2. 主键统一使用 id；外键使用 entity_id。
3. 布尔字段使用 enabled、locked、resolved 等肯定语义。
4. 时间字段使用 _at，毫秒兼容字段使用 _ms。
5. 版本字段使用 version 或 state_version。
6. 逻辑删除字段使用 deleted_at，不使用含义不清的 del。
7. JSONB 扩展字段统一命名为 extra_info、metadata 或 config_json。
8. 设备标识使用 device_id，不能在新表中用 robot_id 代替设备标识。

### 9.18.2 兼容字段

历史代码中存在 robot_id、timestamp、module、type、level、error_code、error_info 和 value 等字段。迁移时可保留兼容字段或建立视图，但新代码统一使用明确的 device_id、occurred_at、alarm_type、severity、message 和 value。

## 9.21 数据模型约束

### 9.21.1 主键与外键

设备、用户和高频历史表优先使用 BIGSERIAL 或 BIGINT 主键；任务、任务运行、任务点位和操作记录使用 UUID，避免跨服务生成编号时发生冲突。外键字段必须与被引用主键类型一致，并根据历史保留要求决定是否允许级联删除。

### 9.21.2 删除策略

用户、设备、任务和系统配置优先使用逻辑删除或禁用；审计、告警、任务运行和设备历史原则上只追加、不物理删除。任务定义删除前必须检查是否存在运行实例，历史运行记录不能因为删除任务定义而失去来源。

### 9.21.3 状态与事件分离

当前状态表用于快速查询，事件表用于追踪变化。更新当前状态时，如果该变化需要通知、审计或历史追溯，必须在同一事务中写入对应事件或 Outbox 记录。

### 9.21.4 外部文件引用

图片、视频和诊断文件使用 resource 表保存元数据，核心业务表只保存 resource_id。资源删除、过期和校验失败都必须留下审计或清理记录，不能只删除数据库中的引用。

## 9.33 resource_lock 资源锁表

资源仲裁由 Controller/服务层负责，数据库只保存租约和审计事实。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| resource_id | VARCHAR(64) | PK |
| owner | VARCHAR(128) | 当前拥有者 |
| owner_token_hash | VARCHAR(128) | Token 摘要 |
| owner_epoch | BIGINT | 代次 |
| locked_at | TIMESTAMPTZ | 获取时间 |
| expires_at | TIMESTAMPTZ | 过期时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

资源锁更新必须使用乐观条件：

~~~sql
UPDATE resource_lock
   SET owner = :owner,
       owner_token_hash = :token_hash,
       owner_epoch = owner_epoch + 1,
       expires_at = :expires_at,
       updated_at = now()
 WHERE resource_id = :resource_id
   AND (owner IS NULL OR expires_at < now());
~~~

影响行数为 0 时表示获取失败，不能覆盖其他 OWNER。急停不依赖该表的普通锁更新。

| extra_info | JSONB | 原始值、量程和协议状态 |

传感器值不能因为超过阈值就直接覆盖为告警文本。测量值、单位、质量和报警状态分开保存。

## 9.36 alarm_record 告警记录表

### 9.36.1 设计目的

alarm_record 保存告警当前状态和告警事实。告警产生、确认、恢复等变化另写入 alarm_event，避免覆盖历史。

### 9.36.3 告警去重

## 9.41 迁移设计

### 9.41.1 迁移原则

1. 每个迁移脚本有单调递增版本号。
2. 迁移脚本必须幂等或由版本表保证只执行一次。
3. 迁移先新增结构，再迁移数据，最后增加非空和唯一约束。
4. 破坏性删除必须拆成多个版本，并先保留兼容窗口。
5. 一期禁止自动降级数据库。
6. 迁移失败时停止 Backend 启动，不继续使用半完成结构。
7. 迁移脚本写入执行日志，记录版本、开始、结束和结果。

### 9.41.2 schema_version

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| version | BIGINT | PK |
| name | VARCHAR(128) | 迁移名称 |
| checksum | VARCHAR(128) | 脚本摘要 |
| applied_at | TIMESTAMPTZ | 执行时间 |
| applied_by | VARCHAR(64) | 执行账号 |
| duration_ms | BIGINT | 耗时 |

### 9.41.3 MigrationRunner

~~~cpp
class MigrationRunner {
public:
    MigrationRunner(ConnectionPool& pool, MigrationManifest manifest);

    void validateCurrentVersion();
    void migrateToLatest();
    MigrationStatus status() const;

private:
    void acquireMigrationLock();
    void releaseMigrationLock();
    void apply(const Migration& migration);
    void verifyChecksum(const Migration& migration);

    ConnectionPool& pool_;

~~~

多个 Backend 实例同时启动时使用 PostgreSQL advisory lock 或专用迁移锁表，确保只有一个实例执行迁移。

## 9.42 典型迁移顺序

~~~text
创建 schema_version
  -> 创建 user/role/permission
  -> 创建 device/device_capability
  -> 创建 task/task_point/task_action
  -> 创建 task_run/task_event/operation_record
  -> 创建 sensor_record/resource
  -> 创建 alarm_record/alarm_event
  -> 创建 audit_event/outbox_event/system_config
  -> 创建索引与约束
  -> 导入一期设备注册数据
  -> 校验外键、唯一键和版本
~~~

设备注册数据只在不存在同一 device_id 时插入；不要在每次 Backend 启动时覆盖真实设备配置和运行状态。

## 9.43 查询与分页设计

### 9.43.1 分页参数

~~~cpp
struct PageRequest {
    uint32_t page{1};
    uint32_t page_size{50};
    std::string cursor;
};

struct SortSpec {
    enum class Field {
        CREATED_AT,
        UPDATED_AT,
        OCCURRED_AT,
        SEQUENCE_NO
    };
    Field field{Field::CREATED_AT};
    bool descending{true};
};
~~~

只允许白名单字段作为排序字段。大数据量历史查询优先使用基于游标的分页，不使用很大的 OFFSET。

### 9.43.2 时间范围

所有历史查询必须明确起止时间、最大返回数量和排序。未指定时间范围的告警、传感器和设备历史查询必须使用默认上限，避免一次读取全表。

### 9.43.3 查询隔离

读查询使用只读事务或普通查询，不持有长时间写锁。详情页所需的多个查询可以并行，但每个查询必须有单独的超时和结果上限。

## 9.45 并发控制

### 9.45.1 乐观锁

任务、设备配置和系统配置更新使用 version：

~~~sql
UPDATE task
   SET name = :name,
       updated_at = now(),
       version = version + 1
 WHERE id = :task_id
   AND version = :expected_version;
~~~

影响行数为 0 时返回 DB_CONCURRENT_UPDATE，由 service 提示调用方重新读取，而不是覆盖其他用户的修改。

### 9.45.2 行锁

资源租约、告警状态切换和 Outbox 领取可以使用 SELECT ... FOR UPDATE SKIP LOCKED。设备控制动作不应通过长事务持有数据库行锁。

### 9.45.3 隔离级别

默认使用 PostgreSQL READ COMMITTED。只有在明确需要时才使用更高隔离级别，并评估死锁和重试成本。

## 9.46 任务执行与数据库事务边界

~~~mermaid
sequenceDiagram
    participant Controller
    participant DB as db
    participant Device
    participant Outbox

    Controller->>DB: create operation ACCEPTED
    DB-->>Controller: commit operation_id
    Controller->>Device: execute command
    Device-->>Controller: progress/result
    Controller->>DB: update operation result
    Controller->>DB: append task_event
    Controller->>Outbox: insert state notification in same tx
    DB-->>Controller: commit
~~~

数据库事务只记录事实，不包围设备网络调用。设备调用超时、数据库写入失败和结果未知分别处理，不能用数据库事务长时间锁住任务或资源。

## 9.47 告警写入流程

~~~text
收到测量或设备故障事件
  -> 计算 alarm_key
  -> 开启短事务
  -> SELECT alarm_record FOR UPDATE
  -> 不存在：INSERT ACTIVE + INSERT RAISED event
  -> 已存在且仍活动：UPDATE last_occurred/value + 可选 INSERT REMIND
  -> 已恢复：UPDATE CLEARED + INSERT CLEARED event
  -> 写 outbox_event
  -> COMMIT
~~~

同一 alarm_key 的并发事件必须串行化，避免重复创建活动告警。不同设备的告警可以并行处理。

## 9.48 设备状态与历史写入

设备实时状态分为两条路径：

1. 更新 device 当前快照，供列表和快速查询使用。
2. 状态变化或定期采样写入 device_state_history，供历史、诊断和审计使用。

实时状态写入失败时，StateCache 继续保存内存中的最新状态并增加 db_write_pending 指标；状态恢复后按版本或时间补写。不能因为历史落库失败把设备软件状态强制改成离线。

## 9.49 数据库故障处理

### 9.49.1 故障分类

| 故障 | 是否重试 | 处理 |
| --- | --- | --- |
| 连接获取超时 | 有限重试 | 返回池耗尽 |
| 建连失败 | 退避重试 | db 进入 DEGRADED |
| 临时网络断开 | 有限重试 | 失效连接并重建 |
| 死锁 | 事务级重试 | 限制次数并告警 |
| 唯一键冲突 | 不重试 | 返回幂等或业务冲突 |
| 参数/约束错误 | 不重试 | 记录开发/配置错误 |
| 提交结果未知 | 不直接重试写入 | 使用幂等键查询确认 |
| 磁盘满 | 不盲目重试 | 告警、暂停非必要历史写入 |

### 9.49.2 降级策略

数据库不可用时：

- 保留设备控制线程、状态缓存和 STOP/急停通道；
- 拒绝需要持久化确认的新任务创建和关键配置变更；
- 允许有限的状态读取和诊断查询；
- 将可补写的状态、审计和告警事件放入有界内存队列或本地可靠缓冲；
- 队列超过上限时丢弃低优先级历史数据并告警；
- 恢复后按事件序号、幂等键和时间补写。

数据库故障不等于设备安全状态。急停成功必须由硬件、Access、Controller 的实际结果确认，不能因为审计写入成功就判定急停完成。

## 9.50 审计缓冲与补写

~~~cpp
struct PendingDBEvent {
    std::string event_type;
    std::string idempotency_key;
    std::string payload_json;
    uint8_t priority{0};
    timestamp_t created_at_ms{0};
};

class DBWriteBuffer {
public:
    bool push(PendingDBEvent event);
    std::vector<PendingDBEvent> takeBatch(size_t max_count);
    void markCommitted(const std::string& key);
    BufferStats stats() const;
};
~~~

补写规则：

1. 高优先级审计、急停和告警事件优先。
2. 每条事件有幂等键。
3. 补写失败按退避策略重试。
4. 补写成功后记录原始发生时间，而不是当前补写时间替换事件时间。
5. 缓冲满时按优先级丢弃可重建的低价值快照，不丢弃安全事件而不报警。

## 9.51 可靠性与幂等

以下写操作必须幂等：

| 操作 | 幂等键 |
| --- | --- |
| 控制操作记录 | operation_id |
| 任务事件 | task_run_id + sequence_no |
| 告警产生 | alarm_key + active window |
| 审计事件 | event_id |
| Outbox | event_id |
| 设备状态补写 | device_id + state_version |
| 传感器批次 | device_id + sample_id |

重试前先查询幂等键对应记录。不能因为网络超时就无条件重新插入控制操作。

## 9.52 数据保留与归档

建议保留策略：

| 数据 | 在线保留 | 归档策略 |
| --- | --- | --- |
| 当前设备快照 | 长期 | 不归档 |
| 设备状态历史 | 3～12 个月可配置 | 按月归档 |
| 传感器记录 | 3～12 个月可配置 | 按月归档或聚合 |
| 任务运行/事件 | 长期或按项目配置 | 只读归档 |
| 图片资源元数据 | 长期 | 文件按 retention 清理 |
| 活动/最近告警 | 长期 | 已恢复告警按月归档 |
| 审计事件 | 按安全制度 | 只允许追加和归档 |
| Outbox | 发送成功后短期保留 | 定期清理 |

归档前必须完成备份校验。删除历史数据不得影响当前告警、任务运行结果和审计链。

## 9.53 备份与恢复

### 9.53.1 备份内容

1. PostgreSQL 全量基础备份。
2. WAL 或等效增量恢复材料。
3. 数据库迁移脚本和当前 schema 版本。
4. Backend 配置模板，不包含密码。
5. 图片、视频、文件存储的资源清单和校验摘要。

### 9.53.2 恢复流程

~~~text
停止 Backend 写入
  -> 恢复 PostgreSQL
  -> 校验 schema_version
  -> 校验关键表和索引
  -> 校验资源引用
  -> 启动 db 健康检查
  -> 重建设备快照缓存
  -> 重新加载设备注册表
  -> 设备自检
  -> 允许业务写入
~~~

恢复后不自动续跑恢复前未确认完成的机械臂运动或协同任务；相关 task_run 应标记为 UNKNOWN 或 RECOVERY_REQUIRED，交由 Controller 和运维流程处理。

## 9.54 数据安全

1. PostgreSQL 账号采用最小权限，Backend 账号不拥有数据库超级用户权限。
2. 迁移账号与运行账号可以分离。
3. 生产连接按部署要求启用 TLS 或受控本机连接。
4. 用户密码只保存强哈希。
5. 审计、告警和任务历史按照角色授权访问。
6. SQL 日志对参数进行脱敏，不记录密码、Token 和敏感文件路径。
7. JSONB 扩展字段必须限制大小，避免成为任意数据注入通道。
8. 数据导出必须记录审计事件。
9. 数据库备份文件必须加密并限制访问权限。
10. 恢复操作必须记录操作者、时间、版本和校验结果。

## 9.56 日志规范

每条数据库错误日志至少包含：

- trace_id；
- Repository 名称；
- 操作名称；
- 数据库连接或事务标识；
- 错误分类；
- 是否可重试；
- 是否可能提交结果未知；
- 耗时；
- 受影响的业务主键摘要。

日志示例：

~~~text
WARN db transaction commit_unknown
repo=TaskRunRepository operation=update_result
task_run_id=... trace_id=...
retryable=false transaction_unknown=true elapsed_ms=...
~~~

不记录完整 SQL 参数，尤其不记录认证凭据和未经脱敏的 metadata。

## 9.57 异常模型

~~~cpp
enum class DBErrorCode {
    INVALID_CONFIG,
    NOT_READY,
    CONNECTION_FAILED,
    CONNECTION_LOST,
    POOL_EXHAUSTED,
    QUERY_TIMEOUT,
    TRANSACTION_FAILED,
    COMMIT_UNKNOWN,
    DEADLOCK,
    CONSTRAINT_VIOLATION,
    NOT_FOUND,
    CONCURRENT_UPDATE,
    MIGRATION_FAILED,
    STORAGE_FULL,
    BUFFER_FULL
};

class DBException : public std::runtime_error {
public:
    DBException(DBErrorCode code,
                std::string message,
                bool retryable,
                bool transaction_unknown);

    DBErrorCode code() const noexcept;
    bool retryable() const noexcept;
    bool transactionUnknown() const noexcept;
};
~~~

SOCI 异常必须在 db 边界捕获并转换为 DBException。异常不得穿透到设备线程导致设备控制线程退出。

## 9.58 关闭流程

~~~mermaid
sequenceDiagram
    participant Backend
    participant DB as DBManager
    participant Pool as ConnectionPool
    participant Writer as DBWriteBuffer
    participant PG as PostgreSQL

    Backend->>DB: stop(deadline)
    DB->>Pool: reject new acquire
    DB->>Writer: flush bounded batch
    Writer->>PG: commit pending events
    DB->>Pool: wait active leases
    Pool->>PG: close sessions
    DB-->>Backend: stopped or timeout report
~~~

关闭顺序不能等待设备动作完成时继续持有数据库连接。数据库关闭超时必须输出未归还连接、活动事务和待补写事件数量。

## 9.60 故障注入矩阵

| 故障注入 | 预期结果 |
| --- | --- |
| PostgreSQL 未启动 | db 初始化失败，Backend 明确报错 |
| 建连超时 | 有限重试，进入 DEGRADED |
| 连接池耗尽 | 请求返回 POOL_EXHAUSTED，不死锁 |
| 查询超时 | 取消/回收连接，记录 QUERY_TIMEOUT |
| 事务中途断线 | 回滚或标记 COMMIT_UNKNOWN |
| 唯一键冲突 | 返回幂等结果或业务冲突 |
| PostgreSQL 重启 | 连接失效，池重建，其他模块按策略降级 |
| 磁盘满 | 暂停非关键历史写入并告警 |
| 迁移校验和变化 | 拒绝启动，不覆盖历史迁移 |
| Outbox 持续失败 | 进入 FAILED/退避，业务事实仍保留 |
| DBWriteBuffer 满 | 按优先级丢弃低价值事件并告警 |
| 数据库恢复到旧版本 | schema 检查失败，禁止 Backend 写入 |

## 9.61 验收追踪

| 验收项 | 验收标准 |
| --- | --- |
| PostgreSQL 接入 | Backend 可通过配置连接 PostgreSQL，未硬编码端口 |
| SOCI 封装 | service、Device、Controller 不依赖 soci::session |
| Repository | 用户、设备、任务、告警、审计均通过 Repository 访问 |
| 事务 | 任务定义和告警状态更新具备原子性 |
| 设备隔离 | R1 故障不影响 R2、相机和 GAM1 的独立记录 |
| 历史数据 | 设备、任务、传感器、告警、审计可按时间分页查询 |
| 幂等 | 重复命令、任务事件、告警事件不会重复产生事实 |
| 故障降级 | 数据库断开时 STOP/急停路径仍可执行 |
| 迁移 | 空库可初始化，已有库可升级，禁止自动降级 |
| 安全 | 凭据、Token、敏感参数不出现在日志和审计明文中 |
| 备份恢复 | 恢复后可校验 schema、关键数据和资源引用 |

## 9.62 扩展设计

### 9.62.1 读写分离

当数据量和并发增长时，可以在 ConnectionPool 层增加读连接池和写连接池。Repository 接口保持不变，读副本延迟通过查询策略显式处理；需要读到刚提交数据的场景继续使用主库或携带一致性标识。

### 9.62.2 分区与归档

device_state_history、sensor_record、task_event、alarm_event 和 audit_event 可以按月分区。分区策略由迁移和运维脚本实现，不改变业务模型。

### 9.62.3 数据分析

后续可以通过只读视图、物化视图或数据同步任务提供趋势分析、热力图和统计报表。分析查询不能阻塞控制事务，也不能直接修改核心业务表。

### 9.62.4 多数据库兼容

SOCI 允许通过后端抽象支持其他数据库，但一期正式部署只保证 PostgreSQL。若未来需要 SQLite 进行离线仿真或 MySQL 兼容部署，必须重新验证 JSONB、UUID、时间、锁、分页、迁移和并发语义，不能只替换连接字符串。

### 9.62.5 事件溯源扩展

当前方案以关系表保存当前状态和历史事件。后续如需要更强的事件溯源能力，可以扩展 task_event、device_event 和 alarm_event，但仍应为查询提供物化当前状态，避免所有页面都重放完整事件流。

## 9.63 设计检查项

代码和设计评审至少检查：

1. 模块名称是否统一为 db。
2. PostgreSQL 是否由部署环境管理数据目录。
3. SOCI 是否只出现在 db 模块。
4. 是否使用 SOCI_POSTGRESQL，未引入不必要的 ODBC 中间层。
5. Repository 是否隐藏 SQL 和 soci::row。
6. 多 Repository 原子操作是否通过 UnitOfWork。
7. 设备网络调用是否没有包在数据库长事务中。
8. 任务定义、任务运行和任务事件是否分离。
9. 当前状态和历史状态是否分离。
10. 测量值、单位、质量和告警是否分离。
11. 告警是否有稳定的 alarm_key 和事件历史。
12. 控制命令是否有 operation_id 和结果未知语义。
13. 审计是否记录控制、急停、模式、告警和配置变更。
14. Outbox 是否与业务事实在同一事务提交。
15. 数据库断线是否不会阻塞 STOP、急停和 Backend 关闭。
16. 缓冲队列是否有上限、优先级和丢弃告警。
17. 所有外部输入是否通过参数绑定或白名单。
18. 查询是否限制时间范围、分页大小和排序字段。
19. 迁移是否有版本、校验和、锁及失败停止策略。
20. 备份、恢复、归档和敏感数据保护是否有可执行方案。

## 9.64 本章小结

本章完成了 MRSS db 模块的详细设计，明确了 PostgreSQL + SOCI + Repository + ConnectionPool + Transaction 的总体方案，定义了数据库生命周期、连接池、事务、UnitOfWork、数据映射、错误模型、迁移、分页、并发控制、故障降级、备份恢复和可观测性。

本章同时完成了一期核心数据模型设计：用户与权限基础表、设备注册与状态历史、任务/点位/动作、任务运行与事件、命令操作、资源锁、GAM1 传感器记录、图片资源元数据、告警及告警事件、审计事件、Outbox 和系统配置。

一期正式数据库为 PostgreSQL，SOCI 仅作为 C++ 数据访问层；SQLite 不作为正式部署目标，IOC 不进入一期 Backend。通过 Repository 和统一事务边界，上层业务不依赖数据库实现；通过幂等、Outbox、有限缓冲和故障隔离，数据库短时异常不会破坏设备控制、安全停止和任务结果的可追踪性。
