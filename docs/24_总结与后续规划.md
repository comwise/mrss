# 第24章 总结与后续规划

## 24.1 文档总结

本套 MRSS 一期软件详细设计说明书完成了从项目背景、需求分析、总体架构到 Backend、Communication、Controller、Device、Access、db、auth、service、api、core、生命周期、调度、模式仲裁、安全、数据、告警、部署、测试、实施和风险的完整设计。

设计最终收敛到以下实现主线：

~~~text
Web / API / WebSocket
        ↓
auth + service
        ↓
Controller + Scheduler + Resource + Safety
        ↓
Device
        ↓
Access
        ↓
仿真设备或真实设备
        ↓
PostgreSQL / History / Alarm / Audit
~~~

一期不引入 IOC。Backend 统一承载业务状态、任务协同、资源仲裁和软件安全逻辑；EPICS 后续通过 Access 适配，不改变上层业务接口。

## 24.2 一期交付边界

一期明确交付：

1. 两个瑞尔曼机械臂 R1、R2；
2. 海康固定相机 HIK_FIX1；
3. 海康 PTZ 相机 HIK_PTZ1；
4. GAM1 辐射传感器；
5. 仿真、真实和混合适配模式；
6. Web/API/WebSocket；
7. 用户认证、角色和范围权限；
8. Manual/Auto；
9. MOVEJ、JOG、STOP 及协同动作；
10. 任务、点位、动作和调度；
11. OWNER、资源锁和租约；
12. SIM/HW/SW 急停模型；
13. Permit、全局锁存和复位；
14. 设备状态、任务历史、传感器、图片、告警和审计；
15. PostgreSQL + SOCI；
16. 部署、备份、恢复和测试闭环。

## 24.3 核心设计结论

### 24.3.1 统一设备抽象

上层只依赖 Device 接口，Access 层隔离厂商协议、Socket、HTTP、SDK、Modbus 或后续 EPICS。仿真不是临时旁路，而是与真实适配器遵守同一接口、状态和事件语义的验证实现。

### 24.3.2 Controller 与 api 分离

api 是协议处理层，负责 HTTP/WebSocket；Controller 是内部控制层，负责命令队列、执行状态、并发、优先级和停止。两者不再使用同一个 controller 名称表达不同职责。

### 24.3.3 安全、模式和资源分层

- auth 决定用户能否发起操作；
- 模式决定当前运行语境；
- OWNER/资源锁决定控制归属；
- Device 状态决定设备是否就绪；
- Safety Permit 决定最终是否允许运动；
- 急停和硬件回路优先于所有软件权限。

### 24.3.4 结果不确定性

设备网络操作存在超时和断线，系统使用 UNKNOWN 状态表达无法确认的结果，不把“请求已接受”当成“设备已完成”，也不在未知状态下盲目重试或自动复位。

### 24.3.5 数据可追溯

用户、任务、操作、设备、采样、图片、告警和审计通过稳定 ID、trace_id、operation_id、task_run_id 和版本建立关系，保证问题可以从页面追溯到服务、设备和数据库事实。

## 24.4 一期最小闭环

一期最小闭环如下：

~~~mermaid
flowchart TB
    LOGIN[用户登录]
    SELECT[选择设备或任务]
    CHECK[权限/模式/OWNER/资源/Permit]
    EXEC[Controller执行]
    DEVICE[仿真或真实设备]
    RECORD[任务/历史/告警/审计]
    EVENT[WebSocket实时事件]

    LOGIN --> SELECT
    SELECT --> CHECK
    CHECK --> EXEC
    EXEC --> DEVICE
    DEVICE --> RECORD
    RECORD --> EVENT
~~~

验收必须至少覆盖：

- R1 独立 MOVEJ/JOG/STOP；
- R2 独立 MOVEJ/JOG/STOP；
- 双臂协同资源和 barrier；
- 臂到位后相机拍照；
- PTZ 控制和拍照；
- GAM1 采样和历史；
- SIM_ESTOP 阻止运动；
- Manual/Auto 切换；
- 任务、告警和审计。

## 24.5 当前限制

本设计明确以下限制：

1. 一期不提供完整 IOC 拓扑和 IOC 运行依赖；
2. EPICS 接入需要后续 Access 适配和一致性评审；
3. 真实设备协议能力必须以现场 SDK/固件验证为准；
4. 硬件安全回路不由 Backend 替代；
5. 现场操作规程和人员培训属于交付组成部分；
6. 生产容量、吞吐和响应时间必须通过实测确定；
7. 多主机高可用不作为一期默认部署目标；
8. 高级数据分析和复杂视觉算法不作为基础闭环硬依赖。

## 24.6 后续阶段一：真实设备完善

重点：

- 完善瑞尔曼 SDK/协议适配；
- 验证速度、加速度、关节限制和位姿到位；
- 验证 HIK_FIX1/HIK_PTZ1 抓图、PTZ、预置位；
- 验证 GAM1 单位、采样周期和质量；
- 建立现场设备能力矩阵；
- 增加设备固件和适配器兼容测试；
- 完善设备自诊断和维护命令。

原则：只替换 Access/Device 适配实现，上层 API、service、任务、历史和审计保持稳定。

## 24.7 后续阶段二：EPICS/IOC 接入

EPICS 接入前必须完成：

1. 确定 PV 命名和单一事实源；
2. 定义 PV 与 Device 状态映射；
3. 定义读写分离和写入权限；
4. 定义 Access 断线 fail-safe；
5. 定义 Permit、OWNER 和 EPICS 自保护边界；
6. 定义 PV 时间戳、质量和版本；
7. 定义迁移期双读/单写策略；
8. 完成仿真、IOC 和真实设备一致性测试；
9. 明确 IOC 故障不绕过硬件急停；
10. 评审是否将某些状态迁移到 IOC，避免两套状态机并存。

EPICS 只是访问实现，不应重复实现 Backend 的任务、权限和审计事实。

## 24.8 后续阶段三：可靠性和可用性

可扩展方向：

- Backend 多实例和故障转移；
- PostgreSQL 主备和连接切换；
- Outbox 外置；
- 设备适配器进程隔离；
- 远程诊断；
- 配置中心和密钥管理；
- 灰度升级；
- 自动化恢复；
- 更细粒度的容量和 SLO 管理。

任何高可用设计都不能降低急停、Permit 和硬件安全回路的优先级。

## 24.9 后续阶段四：任务和协同能力

可扩展方向：

1. 更复杂的轨迹和协同轨迹；
2. 机械臂与相机、传感器的时间同步；
3. 多工作空间和碰撞约束；
4. 任务模板和参数化；
5. 任务版本比较；
6. 更丰富的补偿动作；
7. 人工确认点和电子签名；
8. 任务仿真回放；
9. 离线计划验证；
10. 运行数据分析。

扩展必须继续使用现有 Task、ExecutionPlan、Resource 和 Safety 接口。

## 24.10 后续阶段五：数据和可观测性

可扩展方向：

- 时间序列或分析副本；
- 设备健康趋势；
- 告警根因分析；
- 任务成功率和 MTBF；
- 轨迹质量分析；
- 图片索引和检索；
- 审计报表；
- 数据保留自动化；
- 运行 SLO 和容量预测。

分析系统只读核心业务数据，不直接控制设备和修改安全状态。

## 24.11 架构演进原则

1. 保持 API 和业务模型向后兼容；
2. 通过 Access 隔离外部协议变化；
3. 通过版本化迁移演进数据库；
4. 通过事件和 Outbox 扩展异步能力；
5. 通过组件化执行器隔离故障；
6. 通过配置而不是分叉代码支持仿真/真实/混合；
7. 通过安全评审控制 Permit 和急停变化；
8. 通过测试追踪矩阵保证设计、代码和验收同步。

## 24.14 总结

MRSS 一期通过 Web + Backend + Device/Access 的统一架构，把用户、任务、控制、设备、数据和安全闭合在一个可验证的软件系统中。设计坚持：

- 一期不引入 IOC，先完成 Backend 最小闭环；
- 仿真、真实和混合共享接口和数据模型；
- Controller 负责内部控制，api 负责接口处理；
- 同设备串行、不同设备可并行；
- STOP 和急停独立于普通业务队列；
- 模式、OWNER、资源和 Permit 分层；
- 单设备故障隔离；
- UNKNOWN 结果不伪造成功；
- PostgreSQL + SOCI 统一持久化；
- 日志、告警和审计完整可追溯；
- 部署、测试、恢复和风险纳入交付。

## 24.15 本章小结

本章总结了 MRSS 一期的交付范围、最小闭环、核心设计结论、当前限制和后续演进方向，明确了真实设备、EPICS/IOC、可靠性、协同任务、数据分析和运维能力的扩展路径。后续所有扩展都应保持安全优先、接口稳定、数据可追溯和故障可隔离。
