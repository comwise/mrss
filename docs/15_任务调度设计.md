# 第15章 任务调度设计

## 15.1 概述

任务调度模块负责从任务定义、定时计划、手动请求和恢复请求中生成可执行的 TaskRun，并按照优先级、模式、资源、设备能力和安全许可组织执行。调度模块只安排“何时、以什么优先级、使用哪些资源执行”，具体设备命令由 Controller 串行下发。

一期调度服务运行在 Backend 内，不引入 IOC。R1、R2、HIK_FIX1、HIK_PTZ1 和 GAM1 通过统一 Device/Access 接口参与任务。仿真、真实和混合模式使用相同的调度状态机。

## 15.2 设计目标

1. 支持手动、单次、定时、周期和循环任务。
2. 支持 Normal、High、Critical 三级任务优先级。
3. 支持双臂独立任务和双臂/相机协同任务。
4. 支持“机械臂到位后拍照”和“采样完成后记录”等动作依赖。
5. 同一设备命令串行，不同设备任务在资源不冲突时并行。
6. Manual 请求优先于 Auto 请求；STOP 和急停不经过普通调度队列。
7. 定时任务采用时间窗和 missed policy，避免系统重启后重复执行。
8. 支持任务暂停、恢复、取消、失败重试和结果未知恢复。
9. 资源申请失败时任务不进入设备执行阶段。
10. 单设备故障只影响相关任务，必要时按协同策略影响整组任务。
11. 任务定义版本和运行快照可追溯。
12. 调度队列有上限、背压和可观测指标。

## 15.3 任务模型

~~~text
Task {
    task_id
    name
    type
    priority
    mode_policy
    schedule
    loop_policy
    resource_policy
    points[]
    enabled
    definition_version
}
~~~

TaskPoint：

~~~text
TaskPoint {
    point_id
    order
    target
    pose
    gait_or_motion
    speed
    navigation_or_execution_policy
    actions[]
    timeout
    retry_policy
}
~~~

一期面向设备协同的 target 可以是 ARM_R1、ARM_R2、ARM_PAIR、HIK_FIX1、HIK_PTZ1、GAM1 或组合资源。

## 15.4 任务类型

| 类型 | 说明 |
| --- | --- |
| MANUAL | 用户立即发起 |
| SINGLE | 指定时间执行一次 |
| TIMED | 按时间计划触发 |
| PERIODIC | 按固定周期执行 |
| LOOP | 完成后按策略继续 |
| RECOVERY | 对 UNKNOWN 或中断结果进行确认 |
| CALIBRATION | 受限维护和校准任务 |

一期自动任务不能在系统处于 MAINTENANCE、FAULT、DISABLED 或急停锁存时启动。

## 15.5 优先级

| 优先级 | 适用场景 | 调度规则 |
| --- | --- | --- |
| CRITICAL | 安全相关恢复、关键维护 | 可抢占等待资源，但不得绕过安全许可 |
| HIGH | 运维经理指定任务、超时补偿 | 高于普通任务排队 |
| NORMAL | 常规巡检、采样、拍照 | 按时间和公平策略执行 |

STOP、软件急停、硬件急停和设备保护不属于任务优先级，它们使用独立安全路径。

Manual 与 Auto 的关系：

~~~text
EMERGENCY/STOP > MANUAL > HIGH AUTO > NORMAL AUTO
~~~

## 15.6 调度器组件

### 15.6.1 Scheduler

~~~text
class Scheduler {
public:
    Result<TaskRunId> submit(SubmitTaskCommand);
    Result<void> pause(TaskRunId);
    Result<void> resume(TaskRunId);
    Result<void> cancel(TaskRunId, CancelReason);
    SchedulerSnapshot snapshot() const;
    void tick(MonotonicTime now);
};
~~~

成员：

~~~text
ReadyQueue ready_queue_
TimedQueue timed_queue_
RunningSet running_
ResourceService& resources_
ExecutionService& execution_
PolicyEngine& policy_
TimerService& timer_
SchedulerConfig config_
~~~

### 15.6.2 ReadyQueue

ReadyQueue 按 priority、eligible_at、created_at 和公平轮转顺序排序。相同优先级不能永远被新任务饿死。

### 15.6.3 TimedQueue

TimedQueue 以服务端 UTC 计划时间保存触发点，同时使用 MonotonicClock 计算等待时长。系统时间跳变时重新计算计划，不重复触发已经消费的 execution_key。

## 15.7 任务状态机

~~~mermaid
stateDiagram-v2
    [*] --> CREATED
    CREATED --> VALIDATING
    VALIDATING --> WAITING_SCHEDULE: timed task
    VALIDATING --> WAITING_RESOURCE: ready
    VALIDATING --> REJECTED: invalid
    WAITING_SCHEDULE --> READY: trigger window
    READY --> WAITING_RESOURCE
    WAITING_RESOURCE --> RUNNING: resources acquired
    WAITING_RESOURCE --> READY: resource unavailable
    RUNNING --> PAUSED: pause accepted
    RUNNING --> SUCCEEDED: all points completed
    RUNNING --> FAILED: confirmed failure
    RUNNING --> UNKNOWN: result uncertain
    RUNNING --> CANCELLED: cancelled
    PAUSED --> RUNNING: resumed
    PAUSED --> CANCELLED: cancelled
    UNKNOWN --> RECOVERING
    RECOVERING --> SUCCEEDED: confirmed
    RECOVERING --> FAILED: compensation failed
~~~

每次状态变化写入 TaskEvent，状态转换必须经过白名单。

## 15.8 调度循环

调度循环每次执行：

1. 读取当前单调时间和 UTC 时间；
2. 处理到期定时任务；
3. 应用 missed policy；
4. 将符合条件的任务放入 ReadyQueue；
5. 检查系统模式和 Safety Permit；
6. 计算资源请求；
7. 尝试原子申请资源；
8. 选择可执行 TaskRun；
9. 创建 ExecutionContext；
10. 提交 Controller；
11. 记录调度结果和指标；
12. 处理完成、失败、取消和超时事件。

调度循环不直接调用厂商设备 API。

## 15.9 定时任务触发窗口

一期 Timed 任务默认采用目标时间前后 ±2.5 分钟的触发窗。窗口只用于判断是否允许触发，不表示可以执行两次。

触发规则：

- 当前时间早于窗口：WAITING_SCHEDULE；
- 进入窗口且未消费：生成一次 execution_key；
- 超过窗口且未执行：按 missed_policy 处理；
- 任务重启恢复：检查 execution_key 和 last_triggered_at；
- 系统时钟回拨：不重新消费已完成 key。

支持的 missed_policy：

| 策略 | 行为 |
| --- | --- |
| SKIP | 错过则记录 MISSED 并跳过 |
| RUN_ONCE | 恢复后补执行一次 |
| RUN_NEXT | 放弃本次，等待下一周期 |
| MANUAL_CONFIRM | 进入待确认队列 |

## 15.10 循环任务

LoopPolicy 包含：

~~~text
max_iterations
interval
stop_on_error
stop_on_alarm_level
stop_on_manual
stop_on_estop
~~~

循环任务每次迭代创建 TaskRun 或 TaskIteration，具体选择由数据量和历史查询要求决定。至少保存 iteration_no、started_at、finished_at、result 和 reason。

循环任务不能在急停恢复后自动继续，除非安全复位策略和任务策略都允许。

## 15.11 任务执行计划

ExecutionPlan 是任务定义的不可变运行快照：

~~~text
ExecutionPlan {
    task_id
    definition_version
    run_id
    steps[]
    required_devices[]
    required_resources[]
    dependencies[]
    timeout_policy
}
~~~

计划中显式记录：

- 点位顺序；
- 并行组；
- 前置条件；
- 设备动作；
- 到位条件；
- 拍照/采样触发条件；
- 超时和重试；
- 失败后的补偿；
- 资源释放策略。

## 15.12 协同计划

### 15.12.1 双臂协同

双臂协同步骤使用 barrier：

~~~text
ARM_R1 move to pose A
ARM_R2 move to pose B
barrier: both arrived
next action
~~~

任一机械臂到达超时或故障时，协同组进入 COORDINATION_FAILED，Controller 按安全策略停止另一机械臂，任务记录明确失败原因。

### 15.12.2 臂到位后拍照

~~~mermaid
sequenceDiagram
    participant S as Scheduler
    participant C as Controller
    participant R as Arm
    participant V as Camera
    participant H as History

    S->>C: submit arm move
    C->>R: MOVEJ
    R-->>C: ARRIVED
    C->>C: verify pose and permit
    C->>V: SNAPSHOT
    V-->>C: image result
    C->>H: record arm pose and image relation
    C-->>S: point succeeded
~~~

只有收到设备确认的 ARRIVED/POSE_VALID，才允许触发拍照。位置未知时不得拍照并标记动作结果 UNKNOWN 或 FAILED。

### 15.12.3 采样协同

GAM1 采样动作需要检查传感器 Permit、连接状态和采样间隔；采样结果和触发点位使用同一个 operation_id 关联。

## 15.13 资源申请

任务进入 WAITING_RESOURCE 后构造 ResourceRequest：

~~~text
ResourceRequest {
    owner_id
    resources[]
    mode
    priority
    lease_ttl
    workspace_constraints
}
~~~

双臂任务至少申请 ARM_R1、ARM_R2 和相应工作空间；臂+相机任务申请机械臂、相机和共享工作空间。申请失败不占用部分资源。

## 15.14 并发与公平

调度策略：

1. 设备互不冲突时允许并行；
2. 同一设备只能有一个运行命令；
3. 同一工作空间资源只能有一个独占租约；
4. 高优先级任务可以优先获得空闲资源；
5. 已运行任务不被普通新任务强行打断；
6. Manual 请求可以使等待中的 Auto 任务暂停或延后；
7. 长时间等待的任务提升 aging_score，避免饥饿；
8. 协同任务只有资源全部满足才启动。

## 15.15 超时与重试

超时分层：

- queue_timeout：等待调度；
- resource_timeout：等待资源；
- command_timeout：单个设备命令；
- point_timeout：点位总时长；
- task_timeout：任务总时长；
- recovery_timeout：结果确认。

重试策略包含最大次数、退避、可重试错误白名单和是否重新申请资源。STOP、急停、硬件安全输入和不可逆动作默认不自动重试。

## 15.16 取消、暂停和抢占

取消流程：

1. 标记 CANCEL_REQUESTED；
2. 阻止新点位开始；
3. 对可取消命令发出取消；
4. 必要时向设备发送 STOP；
5. 等待或确认设备状态；
6. 释放资源；
7. 写入 CANCELLED 事件。

暂停只允许在任务策略定义的安全边界执行。正在 MOVEJ 的机械臂不能把“暂停”理解为任意时刻冻结；必须由 Controller 执行受控停止，之后才能进入 PAUSED。

## 15.17 结果未知恢复

设备命令网络超时但设备可能已执行时，任务不得直接重试。处理：

1. 标记 operation UNKNOWN；
2. 查询设备当前状态和命令标识；
3. 若设备支持，查询命令结果；
4. 无法确认时进入人工确认或补偿流程；
5. 记录是否发出过 STOP；
6. 确认后更新 TaskRun 和历史。

这样避免 MOVEJ、拍照或采样被重复执行。

## 15.18 调度持久化

调度器需要持久化：

- TaskRun；
- TaskEvent；
- execution_key；
- operation；
- resource lease；
- 当前计划版本；
- 重试计数；
- missed 结果；
- scheduler checkpoint。

ready queue 可以在重启时从数据库重建，不把内存队列作为唯一事实来源。

## 15.19 监控指标

~~~text
scheduler_ready_queue_depth
scheduler_timed_queue_depth
scheduler_running_tasks
scheduler_resource_wait_seconds
scheduler_task_start_latency
scheduler_task_success_total
scheduler_task_failure_total
scheduler_task_unknown_total
scheduler_missed_total
scheduler_preemption_total
scheduler_queue_reject_total
~~~

指标标签限制为 task_type、priority、device_group 和 result，不使用高基数 task_id 作为长期时序标签。

## 15.20 故障处理

| 故障 | 处理 |
| --- | --- |
| 调度线程异常 | 标记 scheduler unhealthy，停止新任务，保留安全停止 |
| 数据库断开 | 已运行任务继续按内存策略，关键状态进入缓冲 |
| 单设备离线 | 相关任务失败或等待，其他设备继续 |
| 资源锁失效 | 停止相关执行并重新仲裁 |
| 时钟异常 | 暂停定时触发，记录时间故障 |
| 事件总线拥塞 | 控制结果优先，普通状态合并 |
| 进程重启 | 重建队列，UNKNOWN 进入恢复 |
| 全局急停 | 所有运行任务进入 SAFETY_STOPPED |

## 15.21 测试设计

1. 单次、定时、周期和循环任务；
2. ±2.5 分钟触发窗边界；
3. 时钟回拨、跳跃和重启；
4. Normal/High/Critical 优先级；
5. Manual 抢占等待中的 Auto；
6. 同设备串行、跨设备并行；
7. 双臂 barrier 和臂到位拍照；
8. 资源申请全部成功或全部失败；
9. 超时、退避、取消、暂停和恢复；
10. 设备结果 UNKNOWN；
11. 数据库断开和队列重建；
12. 急停期间不启动新动作；
13. 任务版本快照和审计完整性。

## 15.22 验收追踪

- 任务定义、运行计划和执行结果分离；
- 定时任务不会因重启重复执行；
- Manual 高于 Auto，STOP/急停独立于调度队列；
- 同设备串行、不同设备可并行；
- 双臂协同资源原子申请；
- 臂到位后才能触发相机；
- UNKNOWN 不被自动当作成功或盲目重试；
- 任务、操作、资源和审计可关联；
- 单设备故障不影响无关任务；
- 仿真/真实/混合模式调度语义一致。

## 15.23 本章小结

本章完成了 MRSS 任务调度设计，定义了任务模型、优先级、定时窗口、循环、执行计划、协同 barrier、资源申请、并发、公平、超时、重试、取消、恢复和调度持久化。调度器负责组织执行，Controller 负责设备命令，安全停止和急停始终拥有高于普通任务的独立路径。
