# 第18章 数据与历史记录设计

## 18.1 概述

数据模块负责 MRSS 运行过程中用户、设备、任务、动作、操作、采样、图片、告警、审计和系统状态的统一记录、查询、归档与恢复。数据设计区分当前状态、业务事实、事件历史、媒体资源和运行日志，避免把所有信息塞入一张表或只依赖内存状态。

一期使用 PostgreSQL + SOCI。Web、Backend、仿真设备和真实设备使用同一数据模型。图片和其他大文件保存在受控文件系统或后续对象存储中，数据库保存资源元数据和受控引用。

## 18.2 设计目标

1. 当前状态可快速读取，历史事实可完整追溯。
2. 所有控制命令具备 operation_id、trace_id 和结果状态。
3. 任务定义、任务运行和任务事件相互分离。
4. 设备状态、采样值、告警和审计按设备/主体隔离。
5. 记录仿真、真实和混合模式来源。
6. 支持 UTC 时间、毫秒时间戳和稳定排序。
7. 支持分页、时间范围、设备、任务、级别和质量查询。
8. 支持图片资源与动作、点位和任务关联。
9. 关键事实在事务中写入，普通高频状态可批量缓冲。
10. 具备保留、归档、备份、恢复和脱敏策略。
11. 数据库故障不阻塞安全停止。
12. 支持后续分区、读写分离和分析扩展。

## 18.3 数据分类

| 类别 | 示例 | 一致性要求 |
| --- | --- | --- |
| 主数据 | 用户、角色、设备、配置 | 强一致、版本化 |
| 当前状态 | 设备状态、模式、Permit、告警当前态 | 读写快速、可重建 |
| 业务事实 | 任务、操作、采样、图片、告警事件 | 不可随意覆盖 |
| 事件流 | TaskEvent、DeviceEvent、AuditEvent | 追加、幂等 |
| 运行日志 | 应用日志、通信日志、诊断 | 可轮转、可检索 |
| 媒体资源 | 图片、缩略图、路径、校验和 | 文件与元数据一致 |
| 配置快照 | 任务版本、安全参数、设备配置 | 可回滚但不自动降级 |

## 18.4 时间和排序

业务事件统一使用 UTC。数据库优先使用 TIMESTAMPTZ；与旧系统兼容的 BIGINT 时间戳明确为 Unix milliseconds。

稳定排序键：

~~~text
occurred_at ASC/DESC, id ASC/DESC
~~~

客户端提供的时间只作为查询条件，不能作为服务端事件发生时间。时间来源不可信时标记 clock_quality=UNSYNCED。

## 18.5 设备数据

### 18.5.1 Device

保存设备静态注册：

~~~text
device_id
device_type
display_name
adapter_kind
simulation_mode
config_version
enabled
created_at
updated_at
~~~

一期设备：

| device_id | 类型 | 说明 |
| --- | --- | --- |
| R1 | Realman arm | 机械臂1 |
| R2 | Realman arm | 机械臂2 |
| HIK_FIX1 | Hikvision fixed camera | 固定相机 |
| HIK_PTZ1 | Hikvision PTZ camera | 云台相机 |
| GAM1 | radiation sensor | 辐射传感器 |

### 18.5.2 DeviceStateCurrent

只保存当前快照：

~~~text
device_id
state
mode
connection
permit
fault_code
owner_id
position_summary
last_update_at
quality
version
~~~

### 18.5.3 DeviceStateHistory

状态变化和周期快照追加写入：

~~~text
id
device_id
state
mode
connection
permit
fault_code
payload
occurred_at
source
trace_id

~~~

状态不变化时可以按采样周期记录摘要，但高频周期要有保留策略。

## 18.6 任务数据

任务相关表：

~~~text
task
task_point
point_action
task_definition_version
task_run
task_run_point
task_event
~~~

设计原则：

1. task 保存当前定义；
2. task_definition_version 保存不可变版本；
3. task_run 记录某次执行；
4. task_run_point 记录点位执行；
5. task_event 记录状态、进度、错误和恢复；
6. 运行历史引用 definition_version，不受后续编辑影响。

## 18.7 操作数据

Operation 表记录所有可追踪控制动作：

~~~text
operation_id
operation_type
actor_type
actor_id
device_id
task_run_id
status
request_payload_digest
accepted_at
started_at
finished_at
error_code
result_summary
trace_id
idempotency_key
~~~

request_payload_digest 只保存请求摘要，不保存不必要的敏感原文。真实图片、Token 和密码不应进入操作表。

## 18.8 传感器记录

GAM1 采样使用统一结构：

~~~text
sensor_record {
    id
    device_id
    metric_name
    value
    unit
    quality
    sample_time
    received_at
    alarm_level
    operation_id
    task_run_id
    trace_id
    extra_info
}
~~~

value 为数值，unit 为字符串。不同单位不得直接比较；阈值配置必须带 unit 和 metric_name。quality 至少包括 GOOD、BAD、UNCERTAIN、STALE、UNSYNCED。

## 18.9 图片资源

图片数据分为：

- ImageResource：文件或对象元数据；
- ImageRelation：与设备、任务、点位、动作和位置的关联；
- ImageProcessing：缩略图、识别、校验和处理状态。

字段：

~~~text
image_id
storage_kind
relative_path_or_uri
sha256
size_bytes
mime_type
captured_at
device_id
task_run_id
point_id
operation_id
status
retention_until
~~~

路径必须是相对受控根目录的引用。API 不直接暴露任意文件系统路径，下载通过授权资源接口。

## 18.10 告警和历史关系

AlarmState 保存当前告警，AlarmEvent 保存状态变化。采样值或设备状态触发告警时，使用同一个 trace_id 和 source_event_id 关联：

~~~text
sensor_record -> alarm_event -> alarm_state
device_event  -> alarm_event -> alarm_state
task_event    -> alarm_event -> alarm_state
~~~

确认、恢复和关闭都是新的事件，不覆盖首次发生时间。

## 18.11 审计数据

AuditEvent 至少包含：

~~~text
audit_id
occurred_at
actor_type
actor_id
session_id
action
resource_type
resource_id
operation_id
trace_id
result
reason
before_digest
after_digest
source_ip_hash
metadata
~~~

before/after 只保存变更摘要或脱敏字段。安全动作和权限变更不得仅写普通日志而不写 AuditEvent。

## 18.12 当前状态与历史同步

推荐写入流程：

1. 接收设备或业务事件；
2. 在内存中校验版本和时间；
3. 更新当前状态；
4. 追加历史事件；
5. 写入必要的告警/审计/Outbox；
6. 在短事务中提交；
7. 发布事件；
8. 更新指标。

当前状态提交成功而历史失败时，记录 DATA_INCONSISTENCY 并由补偿任务从事件或设备快照重建。历史写失败不能让安全停止失败。

## 18.13 高频采样策略

对于设备状态和 GAM1 数据：

- 关键变化立即写入；
- 周期采样按配置间隔批量写入；
- 相同值和相同质量可以合并；
- 质量从 GOOD 变 BAD 必须立即写入；
- 超阈值变化必须立即触发告警；
- 缓冲有上限；
- 丢弃低价值采样必须增加 dropped_count；
- 不得丢弃急停、故障、告警和控制结果。

## 18.14 查询模型

统一查询参数：

~~~text
from
to
device_id
task_id
task_run_id
operation_id
level
status
quality
page
page_size
sort
~~~

查询限制：

1. page_size 有最大值；
2. 时间范围有最大跨度；
3. 复杂过滤需要索引；
4. 默认按时间倒序；
5. 分页使用稳定游标或 offset 上限；
6. 查询结果按权限过滤；
7. 大型历史导出使用后台任务，不占用 API 工作线程。

## 18.15 索引设计

核心索引方向：

| 表 | 索引 |
| --- | --- |
| device_state_history | device_id, occurred_at |
| sensor_record | device_id, metric_name, sample_time |
| task_event | task_run_id, occurred_at |
| operation | device_id, accepted_at; status |
| alarm_event | alarm_id, occurred_at |
| audit_event | actor_id, occurred_at; resource_id |
| image_resource | task_run_id, captured_at |
| outbox_event | status, next_attempt_at |

索引必须结合实际查询计划验证，不能为了所有字段盲目建立索引。

## 18.16 数据质量

每条外部测量记录至少有：

~~~text
source
received_at
measured_at
quality
unit
calibration_version
sequence
~~~

Source 用于区分 SIM、REAL、MIXED 和设备适配器。序号和版本用于检测乱序、重复和回退。

## 18.17 幂等与重复数据

幂等键可以来自：

- operation_id；
- idempotency_key；
- device_id + source_sequence；
- task_run_id + point_id + attempt_no；
- image_id；
- alarm_key + source_event_id。

重复事件再次到达时：

1. 查询唯一约束；
2. 如果结果已存在且摘要一致，返回原结果；
3. 如果摘要不一致，产生 DATA_CONFLICT；
4. 不静默覆盖原事实。

## 18.18 数据保留

保留策略按数据类型配置：

| 数据 | 策略 |
| --- | --- |
| 当前状态 | 保留当前版本 |
| 任务和审计 | 长期保留或按合规策略 |
| 高频状态 | 按月归档 |
| GAM1 采样 | 按业务和存储容量 |
| 图片 | 按任务、容量和 retention_until |
| 应用日志 | 按天轮转 |
| 告警事件 | 长期保留 |
| Outbox | 成功发送后延迟清理 |

保留策略不能删除仍被审计、任务或告警引用的资源元数据。

## 18.19 归档与分区

可分区表：

~~~text
device_state_history
sensor_record
task_event
alarm_event
audit_event
~~~

一期可以先使用单表 + 索引，数据量达到阈值后按月分区。分区迁移必须在低峰执行，且先验证查询、备份和恢复。

归档后保留摘要、时间范围、设备、任务和归档位置，前端查询可以通过统一 HistoryService 访问在线库和归档库。

## 18.20 备份与恢复

备份至少包括：

- PostgreSQL 全量或基础备份；
- WAL/增量日志；
- 配置文件和版本；
- 图片资源；
- 迁移版本和校验和；
- 密钥引用信息，不备份明文密钥。

恢复流程：

1. 恢复数据库；
2. 校验 schema 和迁移版本；
3. 恢复配置和资源；
4. 校验图片 checksum；
5. 进行数据一致性检查；
6. 以 SAFE_INIT 启动；
7. 重建当前设备状态；
8. 将未确认操作标记 UNKNOWN；
9. 人工确认后再进入运行模式。

## 18.21 数据脱敏和权限

- READ_ONLY 可以查看状态、历史和非敏感告警；
- 审计详情按角色和范围限制；
- 图片访问必须验证任务和设备范围；
- source_ip 使用哈希或脱敏；
- 用户密码、Token、设备凭据不进入历史；
- 导出文件记录导出人、时间、范围和审计号；
- 删除或归档操作需要管理员权限并保留审计。

## 18.22 一致性校验任务

周期任务检查：

1. task_run 是否引用存在的 task definition；
2. operation 是否引用存在的 device；
3. image relation 是否存在资源；
4. alarm_state 是否存在对应事件；
5. current state version 是否不低于历史版本；
6. lease 是否存在 owner；
7. Outbox 是否仍可重试；
8. 资源引用是否未超过 retention；
9. 采样单位和 metric_name 是否匹配；
10. 数据库约束和索引是否正常。

发现问题只修复有明确规则的情况，否则生成 DATA_INCONSISTENCY 告警，禁止静默改历史。

## 18.23 测试设计

1. 当前状态和历史追加；
2. 任务版本快照；
3. 操作幂等和结果 UNKNOWN；
4. GAM1 单位、质量和阈值；
5. 图片文件、元数据和校验和；
6. 审计字段和脱敏；
7. 分页、排序、时间范围；
8. 高频写入和批量提交；
9. 数据库断开和补写；
10. 分区、归档和恢复；
11. 重复、乱序、冲突事件；
12. 权限过滤和导出审计；
13. 备份恢复后安全启动。

## 18.24 验收追踪

- 当前状态和历史数据职责分离；
- 任务、操作、采样、图片、告警和审计可关联；
- 时间、单位、质量和来源明确；
- 高频数据有缓冲上限和丢弃指标；
- 关键控制、安全和告警事实不可静默丢失；
- 数据库恢复后系统从 SAFE_INIT 开始；
- 仿真和真实数据共享同一模型；
- 数据查询、归档、备份和恢复可执行。

## 18.25 本章小结

本章完成了 MRSS 数据与历史记录设计，定义了数据分类、时间语义、设备状态、任务运行、操作、GAM1 采样、图片资源、告警、审计、查询、质量、幂等、保留、归档、备份和恢复。数据层以“当前状态可用、业务事实可追溯、异常结果不伪造、安全事件不丢失”为基本原则。
