# 第2章 需求分析

## 2.1 概述

本章在第1章确定的建设目标和一期范围基础上，对 MRSS 的业务需求、功能需求、数据需求、接口需求、性能要求、安全要求及验收要求进行分析。

MRSS 一期应形成“用户操作—Backend 校验与调度—设备执行—状态反馈—数据记录—异常处置”的完整闭环。系统以 Web 和 Backend 为核心，通过统一设备接口连接仿真设备和真实设备；一期不引入 IOC，设备协同、状态管理、资源仲裁与软件安全联锁均由 Backend 负责。

## 2.2 需求目标

一期需求目标如下：

1. 为多种异构设备建立统一接入、管理、控制和状态反馈机制。
2. 支持两台瑞尔曼机械臂独立运行及协同运行。
3. 支持两类海康相机独立控制，以及机械臂到位后触发相机拍照。
4. 支持辐射传感器连续采集、历史存储和阈值报警。
5. 支持点动、单点运动、连续轨迹和协同轨迹四类运动命令。
6. 支持 Manual、Auto 两种运行模式，并对模式切换进行权限与状态校验。
7. 通过 OWNER 和资源锁避免多个用户、任务或控制源同时操作同一资源。
8. 统一处理仿真急停、硬件急停和软件急停，并实现全局急停锁存。
9. 保证单设备故障隔离，避免无关设备和任务被无条件停止。
10. 保证仿真、真实和混合环境使用一致的 API、业务流程和数据模型。
11. 对用户操作、设备状态、任务过程、报警和安全事件进行记录和追踪。

## 2.3 系统参与者

| 参与者 | 主要职责 |
| --- | --- |
| 超级管理员 | 管理系统管理员、角色、权限及系统级配置 |
| 系统管理员 | 管理用户、设备、运行参数、告警规则及系统维护 |
| 运维经理 | 管理任务、查看全部设备与记录、处理告警、审核关键操作 |
| 运维用户 | 监控设备、执行授权范围内的手动操作和任务操作 |
| 只读用户 | 查看实时状态、任务进度、告警和历史记录，不可下发控制命令 |
| 外部设备 | 接收 Backend 控制命令，返回状态、执行结果和采集数据 |
| 仿真组件 | 按统一设备接口模拟正常、超时、离线、故障和恢复行为 |
| 硬件安全系统 | 提供硬件急停状态；独立完成硬件级安全保护 |

## 2.4 用户与权限需求

### 2.4.1 用户认证

系统应提供用户登录、退出、令牌校验和会话失效能力，并满足以下要求：

- 用户密码不得以明文存储；
- 登录成功后签发具有有效期的访问令牌；
- 禁用、删除或权限变更后的用户不得继续获得超出当前授权的访问；
- 认证失败不得泄露用户是否存在、密码规则或内部异常信息；
- 关键认证事件应写入审计记录。

### 2.4.2 角色权限

系统采用基于角色的访问控制。权限至少划分为查看、操作、配置、维护、审计和系统管理等类别。

| 功能 | 超级管理员 | 系统管理员 | 运维经理 | 运维用户 | 只读用户 |
| --- | --- | --- | --- | --- | --- |
| 实时状态查看 | 允许 | 允许 | 允许 | 允许 | 允许 |
| 历史与告警查看 | 允许 | 允许 | 允许 | 按授权 | 允许 |
| 手动设备控制 | 按配置 | 按配置 | 允许 | 按授权 | 禁止 |
| 自动任务管理 | 允许 | 允许 | 允许 | 按授权 | 禁止 |
| 告警确认与处理 | 允许 | 允许 | 允许 | 按授权 | 禁止 |
| 用户与角色管理 | 允许 | 允许 | 禁止 | 禁止 | 禁止 |
| 系统与设备配置 | 允许 | 允许 | 按授权 | 禁止 | 禁止 |
| 审计记录查看 | 允许 | 允许 | 按授权 | 禁止 | 禁止 |

具体权限不得仅依赖前端隐藏按钮，Backend 必须对每个受保护请求执行授权校验。

## 2.5 设备管理需求

### 2.5.1 统一设备模型

每台设备应具有唯一标识、名称、类型、型号、连接参数、启用状态、运行模式、在线状态、工作状态、故障状态和适配器类型。

设备状态至少包括：

| 状态 | 含义 |
| --- | --- |
| OFFLINE | 设备离线或通信不可用 |
| ONLINE | 设备已连接，但尚未进入可执行状态 |
| IDLE | 设备在线且空闲 |
| RUNNING | 设备正在执行命令或任务 |
| FAULT | 设备发生故障 |
| MAINTENANCE | 设备处于维护状态 |
| DISABLED | 设备被配置为禁用 |

Manual/Auto 为运行模式，不与上述工作状态混为同一枚举。

### 2.5.2 设备生命周期

系统应支持设备配置加载、适配器创建、连接、状态同步、命令执行、断线重连、停止、释放和关闭。单台设备初始化失败时，应记录原因并将其标记为 OFFLINE 或 FAULT，不应导致所有无关设备无法启动。

### 2.5.3 仿真与真实适配

同一设备抽象应能够绑定仿真适配器或真实适配器。适配器由配置选择，支持：

- 全仿真模式；
- 全真实模式；
- 部分真实、部分仿真的混合模式。

切换适配器后，上层 API、服务调用、任务定义及数据库模型应保持不变。

## 2.6 机械臂控制需求

两台瑞尔曼机械臂应支持独立控制和协同控制。单臂基础能力至少包括状态读取、上电、使能、停止、复位、关节状态读取和运动控制。

### 2.6.1 运动命令

| 命令类型 | 需求说明 |
| --- | --- |
| 点动 | 按关节或指定方向持续运动，松开、超时或失去控制权时停止 |
| 单点运动 | 运动至指定关节位置或笛卡尔位姿 |
| 连续轨迹 | 按顺序执行多个轨迹点，并反馈进度和结果 |
| 协同轨迹 | 对两个机械臂或机械臂与其他设备进行统一编排和同步控制 |

所有运动命令执行前必须校验用户权限、运行模式、设备状态、资源所有权、安全状态、参数范围和命令时效。

### 2.6.2 控制结果

控制请求不得仅返回“已接收”。系统应区分请求拒绝、已接收、执行中、成功、失败、超时、取消和急停终止，并提供可关联的命令标识。

## 2.7 相机控制需求

两类海康相机应通过统一相机接口提供以下能力：

- 在线状态与基本信息读取；
- 云台方位角和俯仰角控制；
- 变焦和聚焦控制；
- 实时图像地址或视频流信息获取；
- 抓拍及抓拍结果反馈；
- 超时、离线、认证失败和设备异常处理。

不同型号不支持的能力应通过能力描述明确告知上层，不得以执行期随机失败代替能力判断。

## 2.8 辐射传感器需求

辐射传感器应支持：

1. 周期性采集辐射值、单位、时间戳和设备状态；
2. 对采集数据进行合法性和时效性检查；
3. 保存有效数据，必要时记录无效或异常数据原因；
4. 根据配置的多级阈值产生、升级、恢复和关闭告警；
5. 向 Web 实时推送最新值、趋势和告警变化；
6. 支持仿真数据、超限、离线和数据异常场景。

## 2.9 任务与协同需求

### 2.9.1 任务管理

系统应支持任务创建、编辑、启用、停用、启动、暂停、继续、取消和历史查询。任务定义至少包括任务标识、名称、步骤、涉及资源、执行模式、超时、失败策略及创建者。

### 2.9.2 双臂协同

双臂协同任务应明确两台机械臂的资源占用关系、步骤顺序或同步点。任一机械臂失败时，系统应按任务策略停止关联动作、释放资源并记录失败原因，但不得无条件停止不相关设备。

### 2.9.3 机械臂与相机协同

系统必须支持“机械臂移动到指定位置—确认到位—相机执行拍照—保存结果”的协同流程：

1. 获取机械臂和相机资源锁；
2. 检查两台设备状态及全局安全状态；
3. 控制机械臂移动至目标位姿；
4. 等待到位确认并进行超时判断；
5. 下发相机拍照命令；
6. 保存照片关联信息与步骤结果；
7. 释放资源并完成任务；
8. 任一步失败时按策略停止、回滚或终止，并记录原因。

## 2.10 运行模式与资源仲裁需求

### 2.10.1 Manual 模式

Manual 模式用于授权用户直接操作设备。进入该模式前应确认设备未被自动任务占用；点动命令需要保持机制或超时保护，控制端异常断开后设备必须停止持续运动。

### 2.10.2 Auto 模式

Auto 模式用于调度器和任务执行器控制设备。自动任务开始前必须获得所需资源；任务执行期间，普通手动命令不得抢占资源。急停和具备授权的强制停止除外。

### 2.10.3 OWNER 与资源锁

每个可控制资源应记录当前 OWNER、占用类型、关联用户或任务、获取时间和租约状态。资源锁应满足：

- 同一时刻一个资源只能有一个有效控制所有者；
- 多资源任务采用稳定顺序申请，避免死锁；
- 获取失败时不得保留不完整的资源集合；
- 任务完成、取消、失败或超时后必须释放资源；
- Backend 异常恢复后能够识别并清理失效锁；
- 所有抢占、拒绝和释放行为均应记录。

## 2.11 安全与急停需求

### 2.11.1 急停来源

系统统一管理以下急停来源：

| 来源 | 说明 |
| --- | --- |
| SIM | 仿真环境产生的急停信号 |
| HW | 控制台、机柜或现场硬件急停信号 |
| SW | Web 或 Backend 发起的软件急停命令 |
| GLOBAL | 对各来源进行汇聚后的全局急停状态 |

### 2.11.2 急停行为

任一有效急停源触发后，GLOBAL 应立即进入锁存状态。Backend 应拒绝新的危险动作，并向受影响设备下发停止命令。急停优先级高于模式、任务、OWNER 和普通控制命令。

急停解除不得等同于自动恢复运行。恢复必须满足：

1. 所有急停源均已解除；
2. 授权用户执行复位；
3. 相关设备重新完成状态检查；
4. 原任务不得自动从中断位置继续，除非任务策略明确允许且再次获得授权。

软件机制不能代替硬件安全回路；即使 Backend 或网络失效，硬件急停仍应独立生效。

## 2.12 故障处理需求

故障按影响范围划分为设备级、任务级和系统级：

- 设备级故障仅影响故障设备及依赖该设备的任务；
- 协同步骤失败影响参与该协同过程的资源；
- 数据库或非关键服务短时异常时，应优先维持安全状态并降级运行；
- 全局急停、安全状态不可信或核心控制失效时，升级为系统级阻断；
- 故障恢复后应重新检查设备状态，不得直接假定设备可运行。

系统应为异常提供错误码、错误信息、来源、时间、影响对象和建议处理方式。

## 2.13 数据与历史记录需求

系统至少应管理以下数据：

| 数据类别 | 主要内容 |
| --- | --- |
| 用户与权限 | 用户、角色、权限及关联关系 |
| 设备配置 | 设备标识、型号、连接参数、适配器和能力 |
| 实时状态 | 在线、工作、模式、故障、OWNER 和最新数据 |
| 任务数据 | 任务定义、步骤、资源、状态、进度和执行结果 |
| 传感器数据 | 数值、单位、采集时间、质量和设备标识 |
| 告警记录 | 类型、级别、状态、产生、确认、恢复和关闭时间 |
| 操作审计 | 用户、操作、对象、参数摘要、结果、来源地址和时间 |
| 系统日志 | 模块、级别、消息、上下文和时间 |

历史记录应能够按时间、用户、设备、任务、类型和状态查询。实时状态可采用内存维护，但关键状态变化和执行结果必须持久化。

## 2.14 告警需求

系统应支持设备离线、设备故障、命令失败、任务失败、急停、资源冲突、通信异常和传感器超限等告警。

告警至少包含唯一标识、来源模块、设备、类型、级别、当前状态、数值、单位、说明、产生时间、恢复时间、确认人与确认时间。系统应避免同一持续异常无控制地重复生成告警，可通过活动告警合并和提醒间隔实现抑制。

## 2.15 通信与接口需求

### 2.15.1 Web 接口

Backend 应提供统一 HTTP API 和 WebSocket 实时通道：

- HTTP 用于登录、查询、配置、任务管理及离散控制请求；
- WebSocket 用于设备状态、任务进度、传感器数据、告警及系统事件推送；
- API 应使用统一请求标识、状态码、错误码和响应结构；
- 客户端重连后应能重新获取完整快照，不能只依赖增量消息恢复状态。

### 2.15.2 设备通信

设备接入可使用厂商 SDK、HTTP、TCP 或 UDP，但协议细节仅存在于 access 和具体适配器内部。上层业务不得直接拼装厂商报文。

### 2.15.3 接口幂等与时效

启动、停止、取消、复位等接口应定义幂等行为。运动控制命令应包含请求标识和必要的时间信息，过期或重复命令不得被错误执行。

## 2.16 非功能需求

### 2.16.1 性能

在一期设备规模下，系统应满足：

- 普通 HTTP 查询在正常负载下快速响应；
- 设备状态和告警变化能够及时推送至 Web；
- 急停处理不受普通任务队列阻塞；
- 高频数据采用限频、聚合或批量存储，避免阻塞控制链路；
- 慢设备调用不得占用主通信线程。

具体性能阈值应在部署环境和真实设备联调后通过测试基线固化。

### 2.16.2 可靠性

- Backend 重启后应恢复配置、设备连接及可恢复的运行状态；
- 未完成任务应被明确标记为中断或待人工处理；
- 网络断开、设备超时和数据库短时不可用不得导致进程无控制退出；
- 关键线程和组件异常应被监测并记录；
- 系统关闭时应停止接收新任务、安全终止活动操作并释放资源。

### 2.16.3 可维护性

系统应采用清晰模块边界，公共能力归入 core，第三方库归入 lib。配置、日志和错误码应统一管理。关键模块应具备单元测试接口，并可通过依赖注入替换真实设备。

### 2.16.4 可扩展性

新增同类设备时，应主要增加适配器与配置，不修改上层业务流程。新增命令、任务步骤或告警类型时，应避免破坏现有 API 和历史数据。

### 2.16.5 可观测性

日志、指标、状态和审计记录应包含统一时间、模块、设备、用户、任务和请求关联信息。关键流程能够从用户请求追踪至设备命令和最终结果。

## 2.17 配置需求

系统配置至少包括：

- 服务监听地址、端口和线程参数；
- PostgreSQL 连接与连接池参数；
- JWT 密钥来源和有效期；
- 设备清单、型号、地址、协议及适配器类型；
- 采样周期、超时、重试和重连策略；
- 告警阈值与提醒间隔；
- 日志级别、路径和保留策略；
- 仿真场景及故障注入参数。

敏感配置不得写入公开仓库或普通日志。配置加载失败时应指出具体字段和原因。

## 2.18 约束条件

1. Backend 主要采用 C++17 实现。
2. HTTP/WebSocket 服务沿用 uWebSockets 技术路线。
3. 数据持久化采用 PostgreSQL，并通过 SOCI 建立数据库兼容与访问封装。
4. 配置采用 YAML，认证采用 JWT 和基于角色的权限控制。
5. 一期不依赖 IOC 或 Python 子进程完成核心控制。
6. EPICS 仅作为后续可选接口适配方向。
7. 真实设备 SDK 或协议差异必须封装在 access/DeviceAdapter 范围内。
8. 软件安全逻辑不得替代机械、电气和硬件急停设计。

## 2.19 需求优先级

| 优先级 | 定义 | 一期处理原则 |
| --- | --- | --- |
| P0 | 安全或系统闭环必需 | 必须实现并完成测试 |
| P1 | 一期主要业务能力 | 应实现，阻塞项需明确处置 |
| P2 | 改善使用与维护效率 | 在主链路稳定后实现 |
| P3 | 后续增强能力 | 保留接口或进入后续规划 |

主要需求优先级如下：

| 需求 | 优先级 |
| --- | --- |
| 用户认证与 Backend 权限校验 | P0 |
| 统一设备状态与适配接口 | P0 |
| 急停锁存、命令阻断与人工复位 | P0 |
| OWNER、资源锁和模式仲裁 | P0 |

## 2.20 需求验收与追踪

每项需求应分配唯一编号，并在设计、实现和测试阶段保持关联。建议编号如下：

| 前缀 | 需求类别 | 示例 |
| --- | --- | --- |
| AUTH | 认证与权限 | AUTH-001 |
| DEV | 设备管理 | DEV-001 |
| CTRL | 设备控制 | CTRL-001 |
| TASK | 任务与协同 | TASK-001 |
| MODE | 模式与资源 | MODE-001 |
| SAFE | 安全与急停 | SAFE-001 |
| DATA | 数据与历史 | DATA-001 |
| ALARM | 告警 | ALARM-001 |
| COMM | 通信接口 | COMM-001 |
| NFR | 非功能需求 | NFR-001 |

验收时至少应验证：

1. 正常流程能够完成端到端闭环；
2. 无权限、状态不符、资源冲突和参数非法时请求被正确拒绝；
3. 设备离线、执行失败、超时和断线重连行为符合设计；
4. 任一急停源触发后危险动作被阻断，解除后必须人工复位；
5. 单设备故障不会无条件影响无关设备；
6. 仿真与真实适配器满足同一接口契约；
7. 关键操作、任务结果、告警和安全事件可查询、可关联、可追踪。

## 2.21 本章小结

本章明确了 MRSS 一期的参与者、功能、设备、控制、协同、模式、资源、安全、数据、通信和非功能需求。后续系统总体架构及各模块设计必须以本章为约束，并通过统一需求编号建立设计与测试追踪关系。
